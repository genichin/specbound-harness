> **Lifecycle boundary:** 이 Discovery의 lifecycle state는 frontmatter와 이에 대응하는 content-addressed confirmation record로만 결정된다. 이 문서는 approved requirement가 아니며 implementation, adoption, canonical IQC/DQC publication, Delivery, Merge 또는 Release를 authorize하지 않는다. - **Trigger / initiating change:** 사용자가 기존 규칙과 validator를 실제 IQC/DQC 운영 transition에서 자동 집행할 writer, adoption 및 prospective canary 경로를 구현하고 전향적으로 채택하는 Discovery를 시작하도록 지시했다.
- **Relationship:** `follow-up`
- **관련 Discovery 및 REQ 참조:** `dcy-0001-r1`/`req-0001-r2`는 canonical Micro-SPEC·IQC·DQC topology와 read-side validation을, `dcy-0003-r1`/`req-0003-r2`는 copied-fixture issuance와 immutable-write safety를, `dcy-0004-r1`/`req-0004-r1`은 provider-neutral IQC/DQC agent contract와 authority separation을 다룬다. 이 Discovery는 그 artifact를 대체하지 않고 live repository cutover 경계를 탐색한다.
- **기존 작업의 경미한 갱신이 아니라 새 Discovery가 필요한 이유:** operational adoption authority, live canonical write transaction, canary cutover 및 transition-policy 변경은 기존 REQ의 explicit non-goal이며 lifecycle authority와 repository behavior를 바꾸는 material scope다. 기존 confirmed/approved snapshot을 수정하면 content-addressed provenance가 깨진다.
- **기존 approved scope, 진행 중 작업 또는 released behavior에 미치는 영향:** 현재 validation, copied-fixture issuance, agent contract, approved REQ와 historical Bootstrap evidence는 변경하지 않는다. 이 draft 자체는 production adoption registry, live canonical roots 또는 transition matrix를 변경하지 않는다.

## 2. Problem and target users

- **문제:** 저장소는 Micro-SPEC, iteration-QC, delivery-QC의 canonical schema와 validator, claim validation 및 copied-fixture publication safety를 제공하지만 실제 `specbound-harness` repository에서 exact approved REQ를 operationally adopt하고 authority-bound live IQC/DQC record를 발행하는 canonical transition은 없다. 따라서 implementation source·test·CI evidence가 존재해도 live canonical IQC/DQC lifecycle state로 기록할 수 없고, transition policy는 해당 publication을 기본 `UNSUPPORTED_BLOCKED`로 유지한다.
- **대상 사용자 / 영향받는 시스템:** repository maintainer, implementation 및 IQC/DQC 역할 수행자, configured lifecycle authority, `specbound` CLI/validator, CI, `specbound.yaml`, canonical IQC/DQC roots와 transition-policy 운영자.
- **현재 상태와 evidence:** `policy.control_plane_adoption.requirements`는 빈 배열이고 live `.specbound/iteration-qc`와 `.specbound/delivery-qc` record는 0개다. `issuance-request --publish`는 marked copied fixture에 제한된다. current CLI help는 pre-adoption Micro-SPEC publication만 설명하지만 internal publication boundary는 validated fixture planning/QC artifact를 처리하므로, live support와 fixture proof를 구분하면서 guidance/source contract도 정렬해야 한다.

## 3. Desired outcome and success signals

- **기대 결과:** 후속 REQ가 exact approved REQ snapshot에 대한 accountable operational adoption, authority-bound live IQC/DQC publication, failure-atomic record creation 및 new prospective canary cutover를 하나의 transition-specific governance boundary로 정의할 수 있다.
- **관찰 가능한 성공 신호:** 새로운 작은 canary lifecycle item이 historical artifact를 재분류하지 않고 reviewed Micro-SPEC, exact implementation evidence, live canonical IQC, complete canonical DQC를 real writer·validator·configured authority 경로로 통과하며, 성공한 transition만 `CANONICAL_REQUIRED`로 변경할 수 있는 설계를 review할 수 있다.
- **측정 또는 관찰 방법:** Discovery review에서 adoption owner/artifact, IQC authority, staged cutover와 writer boundary를 결정한다. 후속 approved REQ와 reviewed Micro-SPEC가 존재할 경우 isolated negative/fault tests, supported-platform CI, exact adoption decision, new canary records 및 post-canary root validation으로 관찰한다.

## 12. Recommendation

- **권장 방향:** One follow-up Discovery should govern a staged cutover: first establish an authority-bound adoption decision and live IQC writer/canary, then establish live DQC writer/canary. Each transition changes to `CANONICAL_REQUIRED` only after its own real record validates; Delivery and Merge/Release remain blocked and separate.

- [x] User intent와 agent assumption/recommendation이 구분된다.
- [x] Trigger, lineage 및 관련 Discovery/REQ/delivery 작업 영향이 명시되었거나 부재를 평가했다.
- [x] Problem, target user, desired outcome, scope, Non-goals, 예상 변경 영향이 명시적이다.
- [x] Candidate requirement concern은 non-binding이며 approved Acceptance criteria처럼 보이지 않는다.
- [x] Fact에는 exact path/identity/revision/SHA evidence가 있고 assumption은 label 및 owner가 있다.
- [x] Material alternative, risk, constraint, dependency, decision, Open question을 명시했다.
- [x] 모든 Open question은 stable `OQ-<n>` ID, `DECIDE`/`CONFIRM`/`DATA` type, owner 및 resolution/defer condition을 가진다.
- [x] REQ drafting readiness는 blocking OQ와 confirmation state를 반영하며, 이 문서는 self-confirmation claim을 포함하지 않는다.
- [x] 이 Discovery에 implementation Acceptance criteria, implementation authorization 또는 approval claim이 없다.
- [x] 제안된 다음 action은 exact `in_review` snapshot의 canonical confirmation으로 제한되며 Discovery authority를 초과하지 않는다.
