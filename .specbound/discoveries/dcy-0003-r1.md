# Discovery: Canonical evidence issuance and immutable-write safety

> **Lifecycle boundary:** This Discovery's lifecycle state is determined by its frontmatter and any matching content-addressed confirmation record. ## 0. Discovery context and lineage

- **Trigger / initiating change:** The completed `req-0001-r1` validation slice can validate canonical Micro-SPEC, iteration-QC, and delivery-QC files in copied fixtures, but it deliberately does not issue those records. Its AC-006 verification plan calls for canonical created paths, no-overwrite behavior, digest stability, and rejected-write target absence, which need a separate write-capability boundary.
- **Relationship:** `follow-up`
- **Related Discovery and REQ references:** `.specbound/discoveries/dcy-0001-r1.md` established the evidence-control-plane topic; `docs/requirements/req-0001/req-0001-r1.md` implemented validation-only artifact families. Neither source is modified or superseded by this draft.
- **Why this is a new or revised Discovery rather than a minor update to prior work:** Issuing immutable canonical records introduces distinct write-side behavior, failure atomicity, target allocation, and authority risks. Adding it to the confirmed Discovery or approved REQ in place would break their content-addressed scope.
- **Impact on prior approved scope, in-flight work, or released behavior:** None. Existing validation behavior, manual-bootstrap artifacts, the empty live adoption registry, and all approval bindings remain unchanged. This draft records only a future candidate scope.

## 2. Problem and target users

- **Problem:** Validators can prove that a pre-existing canonical evidence chain is acceptable, but maintainers and delivery agents lack a governed mechanism to create canonical Micro-SPEC, iteration-QC, and delivery-QC records safely. Direct file writes cannot by themselves prove allocation, no-overwrite, atomic failure, or digest-stability behavior.
- **Target users / affected systems:** Repository maintainers and delivery agents creating evidence for a future explicitly adopted REQ; the `specbound` CLI, canonical control-plane roots, templates, fixtures, validator tests, and repository-backed skill guidance.
- **Current state and evidence:** `req-0001-r1` AC-001 through AC-006 establish topology and validation. `ms-0001-006` explicitly states that fixture setup writes evidence and the CLI only validates it. The live adoption registry is intentionally empty.

## 3. Desired outcome and success signals

- **Desired outcome:** A later, separately approved REQ can define a narrow, fail-closed canonical issuance interface that creates exactly one requested evidence artifact only after all preconditions pass and that leaves no target behind after rejection.
- **Observable success signals:** The later REQ can specify deterministic safe-relative target allocation, parent/claim preconditions, no-overwrite and idempotency semantics, atomic write behavior, exact resulting digest reporting, and isolated positive/negative CLI fixtures without granting lifecycle authority.
- **Measurement or observation method:** Review this Discovery's boundaries and open questions; if confirmed and followed by a separately approved REQ, verify the implementation through real CLI copied-fixture tests that inspect created paths, bytes/digests, rejection blockers, and target absence.

> These are outcome-level signals, not implementation acceptance criteria or approval to build an issuance command.

## 3a. Candidate requirement concerns (non-binding)

- **Capability concerns to refine into a REQ:** Explicit draft-only CLI operations for creating one canonical Micro-SPEC, iteration-QC, or delivery-QC artifact; deterministic path/identifier allocation; template-based initial content; structured successful result including safe-relative path and SHA-256.
- **Quality, safety, or operational concerns to refine into a REQ:** Validate all input and authority/adoption preconditions before filesystem mutation; reject absolute/traversal/symlinked paths; never overwrite; use atomic creation; verify output digest; remove or avoid partial targets after any rejection or write error; use copied fixtures for every mutation test.
- **Scope boundaries that a REQ must preserve:** Issuance creates draft/planning or QC evidence only. It must not create approvals, confirmations, adoption entries, delivery decisions, merge authority, release authority, external signatures, or mutate an approved REQ.

These are Discovery hypotheses, not REQ acceptance criteria or approved scope.

## 12. Recommendation

- **Recommended direction:** Keep the first issuance slice local, greenfield, copied-fixture-only, and fail-before-write. Require explicit target identity; validate all parent/adoption/semantic preconditions before atomic exclusive creation; report only safe-relative path and SHA-256; and leave all lifecycle authority outside the command.
- **Why this direction:** It closes the exact proof gap between fixture-authored evidence and executable write safety without enrolling a live REQ or expanding approval/delivery/release authority.
- **Trade-offs accepted or deferred:** A small initial feature and explicit identifiers are preferred over automatic migration or broad orchestration. The adoption policy, parent-precondition granularity, and concurrency boundary are resolved; migration remains deferred rather than implicit.
