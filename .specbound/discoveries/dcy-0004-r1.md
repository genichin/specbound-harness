# Discovery: Lifecycle agent contracts and delegated orchestration

> **Lifecycle boundary:** 이 Discovery의 lifecycle state는 frontmatter와 이에 대응하는 content-addressed confirmation record로만 결정된다. 이 문서는 approved requirement가 아니며 agent 구현, confirmation, approval, implementation, merge, delivery 또는 release를 authorize하지 않는다. REQ draft는 `.specbound/confirmations/dcy-0004-r1.confirmation.json`의 유효한 confirmation record가 이 정확한 `.specbound/discoveries/dcy-0004-r1.md` snapshot에 `permitted_next_action: draft_req_only`로 binding될 때만 허용된다.

## 0. Discovery context 및 lineage

- **Trigger / initiating change:** 사용자가 `DCY → REQ → MS → 구현 → IQC → DQC → Delivery 결정 → Merge/Release` 흐름에서 각 단계의 담당 에이전트와 gate 책임을 명확히 정의해야 한다고 판단하고, 역할별 repository-backed skill과 필요 시 생성되는 독립 서브에이전트 형태를 검토한 뒤 이 내용으로 Discovery를 시작하도록 요청했다.
- **Relationship:** `follow-up`
- **관련 Discovery 및 REQ 참조:** `dcy-0001-r1`과 `req-0001-r1`은 Micro-SPEC/IQC/DQC control plane을, `dcy-0002-r1`과 `req-0002-r1`은 REQ lifecycle을, `dcy-0003-r1`과 `req-0003-r2`는 canonical issuance를 다룬다. 이 Discovery는 기존 artifact를 대체하지 않고 그 위에서 agent responsibility와 orchestration boundary를 탐색한다.
- **기존 작업의 경미한 갱신이 아니라 새 Discovery가 필요한 이유:** Agent identity, 역할별 mutation 권한, 독립 검토, orchestration, human authority와 CLI/CI enforcement의 분리는 기존 승인 범위에 없는 새로운 governance capability다. 기존 hash-bound Discovery나 REQ를 수정하면 provenance를 훼손한다.
- **기존 approved scope, 진행 중 작업 또는 released behavior에 미치는 영향:** 없음. 기존 lifecycle artifact, approval, QC validation 및 issuance 동작은 그대로 유지한다. 이 draft는 후속 요구사항 후보만 탐색한다.

## 1. User intent

- **명시된 의도:** lifecycle 각 단계에 필요한 담당 에이전트를 명확히 정의하고, 역할별 `SKILL.md`를 가진 독립 서브에이전트를 필요할 때 생성하는 형태의 구현 가능성을 Discovery로 검토한다.
- **출처 context:** 2026-07-24 사용자 대화에서 단계별 담당 역할, gate와 author의 분리, 7개 논리적 LLM 역할, Hermes의 동적 서브에이전트 실행 형태를 순차적으로 확인했다.
- **원문 인용 또는 충실한 요약:** “이 내용으로 discovery를 시작하자.”

## 2. Problem and target users

- **문제:** 현재 저장소는 lifecycle artifact, 일부 authoring/review skill, CLI/CI validation과 risk별 authority를 제공하지만, 각 단계에서 어떤 에이전트가 어떤 입력을 받고 무엇을 작성·검토할 수 있으며 어떤 lifecycle claim을 금지해야 하는지에 대한 통일된 agent contract가 없다. 이 상태에서는 orchestrator가 역할을 혼합하거나 작성자가 스스로 gate를 통과시키고, 에이전트 출력이 human authority 또는 deterministic validation으로 오인될 위험이 있다.
- **대상 사용자 / 영향받는 시스템:** SpecBound를 이용해 AI-assisted SDLC를 운영하는 repository maintainer, accountable confirmer/approver, agent orchestrator, author/reviewer/implementation/QC agents, `specbound` CLI, CI와 repository-backed skills.
- **현재 상태와 evidence:** `docs/governance/issue-sdlc.md`는 단계별 입력·출력·blocker를 정의하고, `AGENTS.md`는 CLI와 CI가 enforcement authority라고 명시한다. `specbound.yaml`은 risk별 authority allowlist를 제공한다. 그러나 현재 repository-backed skill은 `specbound-harness`, `confirm-discovery`, `draft-req`, `review-req` 네 개이며 Discovery/REQ/MS author, independent reviewer, implementation, IQC, DQC 역할 전체를 공통 contract로 정의하지 않는다.

## 3. Desired outcome and success signals

- **기대 결과:** 후속 REQ가 lifecycle 역할별 agent contract, 독립성 규칙, 정확한 artifact handoff, 허용된 mutation, 금지된 claim, structured verdict와 human/CLI/CI authority boundary를 명확히 정의할 수 있다.
- **관찰 가능한 성공 신호:** 역할별 책임이 겹치지 않고, orchestrator가 현재 lifecycle state에서 허용된 역할만 호출하며, 각 서브에이전트가 exact path/ID/revision/SHA 입력을 받고 제한된 출력만 생성하고, gate 실패가 `pass/rework/blocked`와 같은 구조화된 결과로 fail-closed 처리되는 설계를 검토할 수 있다.
- **측정 또는 관찰 방법:** Discovery review에서 역할·권한·독립성·provider portability 관련 open question을 해소한다. 이후 별도로 확인된 Discovery와 승인된 REQ가 만들어질 경우 schema/skill fixtures와 CLI/CI 테스트로 허용·금지 동작을 검증한다.

> 이 절은 outcome 수준이며 agent 구현 acceptance criteria가 아니다.

## 6. Scope

- **In scope:** 7개 논리적 LLM 역할의 책임과 경계; role별 입력·출력·허용 도구·허용 mutation·금지 claim; producer/reviewer 분리; orchestrator dispatch 규칙; structured verdict; exact artifact digest handoff; 기존 risk별 authority allowlist와의 연결; repository-backed skill과 machine-readable policy/schema 후보.
- **영향받는 boundary/component:** `skills/`, `specbound.yaml` 또는 후속 policy artifact, future schemas/templates, orchestrator integration, CLI validation, CI fixtures, `docs/governance/issue-sdlc.md`, adopter guidance.
- **Dependency:** 기존 Discovery/REQ/MS/IQC/DQC binding과 issuance control, risk authority policy, Hermes delegation 또는 동등한 isolated subagent runtime, 별도로 확인된 이 Discovery와 승인된 후속 REQ.

### 6a. 첫 후속 REQ의 orchestration boundary

첫 후속 REQ는 **explicit one-shot role invocation**까지만 포함한다.

- **포함:** 호출자가 exact role ID와 target path/ID/revision/SHA를 명시하면 adapter가 lifecycle eligibility와 role policy를 확인하고, 하나의 adapter-configured model로 새 isolated context를 생성하여 정확히 한 역할을 실행하고, 결과를 provider-neutral `agent-result`로 변환하는 경계.
- **포함:** 7개 role skill, machine-readable role policy, result schema, static CLI validation, invalid fixture와 최소 Hermes role-to-skill/tool/workdir/result mapping.
- **제외:** 다음 역할 자동 선택, lifecycle chain 자동 진행, retry/loop/scheduler, 여러 role 동시 orchestration, 자동 status transition, confirmation/approval/delivery decision, merge/release 및 persistent worker/profile 운영.
- **Fail closed:** 호출자가 role 또는 exact target을 생략하거나 current lifecycle state가 그 role을 허용하지 않으면 adapter는 실행 전에 `blocked`를 반환한다.

### 6b. Producer, reviewer, gate, authority 및 executor 경계

| Candidate / stage | Producer LLM role | Independent review 또는 QC | Deterministic gate | Accountable authority / executor | 허용되는 다음 action | Rework destination |
| --- | --- | --- | --- | --- | --- | --- |
| Discovery draft | Discovery Author | Independent Reviewer, 새 context | exact binding 및 `specbound validate` | configured Discovery confirmer가 canonical CLI record를 발행 | `draft_req_only` | Discovery Author |
| REQ draft | Requirement Author | Independent Reviewer, 새 context | non-authorizing `to-in-review`, review evidence, readiness 및 `specbound validate` | configured review-decision/rejection/reconsideration/approval authority가 해당 canonical CLI transition만 수행 | approved REQ에 대한 Micro-SPEC 작성 | Requirement Author |
| Micro-SPEC candidate | Micro-SPEC Author | Independent Reviewer, 새 context | exact parent binding, review record 및 `specbound validate` | configured Micro-SPEC review authority와 canonical CLI | reviewed Micro-SPEC 범위의 implementation | Micro-SPEC Author |
| Implementation slice | Implementation Agent | Iteration-QC Agent, 구현과 다른 context | focused tests, exact MS/REQ binding 및 IQC validation | LLM verdict는 authority가 아니며 verified evidence만 다음 planning/QC 입력이 됨 | 다음 bounded iteration 또는 DQC evidence aggregation | Implementation Agent 또는 Micro-SPEC Author |
| Delivery evidence candidate | Delivery-QC Agent | DQC evidence는 implementation/IQC context와 분리 | complete AC coverage, exact IQC set 및 DQC validation | configured DQC authority가 별도 task에서 canonical record를 발행 | 별도 Delivery decision 검토만 가능 | Delivery-QC Agent 또는 해당 iteration owner |
| Delivery decision | 7개 LLM 역할 밖 | DQC는 evidence일 뿐 decision이 아님 | 기존/후속 governance가 정한 binding | accountable human authority; 첫 REQ에서 executor 구현 제외 | 별도 Merge/Release governance 입력 | evidence owner |
| Merge/Release | 첫 REQ 범위 밖 | 해당 없음 | 별도 Discovery/REQ 필요 | 별도 Agent/Bot contract와 authority 필요 | 별도 governance가 정함 | 별도 governance가 정함 |

- Producer와 그 reviewer, Implementation Agent와 Iteration-QC Agent, Delivery-QC Agent와 Delivery decision authority는 같은 execution/context가 될 수 없다.
- 같은 adapter-configured model alias를 재사용할 수 있지만 각 역할 호출은 새 context/execution ID를 사용한다. Reviewer 입력에는 exact candidate와 허용된 repository evidence만 포함하며 producer의 숨은 reasoning 또는 작성 대화는 전달하지 않는다.
- Reviewer/QC result는 recommendation 또는 evidence다. authority identity, allowlist 검증과 canonical CLI record가 없는 transition을 승인으로 간주하지 않는다.

후속 `agent-result`/policy가 독립성을 검증할 수 있도록 최소한 `role_id`, `execution_id`, `context_id`, `model_alias`, `producer_result_ref`, `reviewer_run_ref`, `authority_type`, `authority_action_id`와 `context_provenance`를 표현한다. `context_provenance`는 producer transcript·session memory 상속 여부와 reviewer에게 전달한 exact repository/evidence reference를 구분한다.

| Pair | 금지 overlap | 허용 overlap |
| --- | --- | --- |
| Producer ↔ Independent Reviewer | 같은 `execution_id`/`context_id`, producer transcript 또는 session memory 상속, reviewer의 candidate mutation | 같은 model alias와 공개 repository evidence |
| Implementation ↔ Iteration-QC | 같은 `execution_id`/`context_id`, IQC의 implementation source mutation | 같은 model alias와 reviewed MS/test evidence |
| Delivery-QC ↔ Delivery authority | 같은 `execution_id`/`context_id`/`authority_action_id`, DQC verdict를 Delivery decision으로 승격 | 같은 model alias; authority는 7개 역할 밖의 별도 explicit action |
| Reviewer/QC ↔ configured lifecycle authority | 같은 run이 verdict와 canonical authority action을 함께 주장 | 현재 `specbound.yaml`이 허용한 authority identity를 별도 run/action에서 사용하는 것; 더 강한 actor separation은 별도 policy가 필요 |
| Producer ↔ human authority | producer LLM run이 human authority 또는 canonical record를 주장 | 같은 accountable repository owner가 기존 allowlist 아래 별도 explicit human action을 수행하는 것 |

### 6c. Existing authority-policy mapping

첫 후속 REQ는 아래의 기존 transition-specific selector를 재사용하며 generic “risk authority”를 새로 만들지 않는다.

| Transition | Canonical risk source | Existing `specbound.yaml` selector | Canonical decision boundary |
| --- | --- | --- | --- |
| Discovery confirmation | Discovery `risk_class` | `discovery_confirmation_authorities_by_risk` | digest-bound confirmation record |
| REQ review submission | 해당 없음 | selector 없음 | `req to-in-review`는 authority 인수가 없는 non-authorizing submission |
| REQ review decision | REQ `risk` | `requirement_review_decision_authorities_by_risk` | digest-bound review decision |
| REQ rejection | REQ `risk` | `requirement_review_authorities_by_risk` | digest-bound rejection record |
| REQ reconsideration | REQ `risk` | `requirement_reconsideration_authorities_by_risk` | digest-bound reconsideration record와 reviewed-state reopening |
| REQ approval | REQ `risk` | `requirement_approval_authorities_by_risk` | digest-bound approval record |
| Micro-SPEC review | inherited REQ risk | `micro_spec_review_authorities_by_risk` | digest-bound Micro-SPEC review record |
| Delivery-QC verification | inherited REQ risk | `delivery_qc_authorities_by_risk` | digest-bound DQC record; Delivery decision은 아님 |
| Delivery decision | 해당 policy가 현재 없음 | unsupported | 첫 후속 REQ에서 `blocked/none` |
| Merge/Release | 해당 policy가 현재 없음 | unsupported | 별도 Discovery/REQ 전까지 `blocked/none` |

## 7. Non-goals

- **명시적으로 제외:** 이 Discovery에서 실제 agent skill 구현, live Hermes profile 설치, 자동 confirmation/approval/delivery decision, agent의 self-approval, 모델/provider 강제, persistent daemon 7개 운영, 기존 approved artifact 수정, merge/release 자동 승인.
- **후속 Discovery 또는 REQ로 defer:** 7-role multi-profile deployment, multi-model routing, 장기 실행 worker pool, cross-repository coordination, cryptographic agent identity, external policy engine, automated merge/release executor, 비용·성능 최적화 정책.

## 7a. 예상 변경 및 영향

- **예상 product/service behavior 변경:** 후속 구현이 승인되면 orchestrator는 lifecycle state에 맞는 역할만 호출하고, 각 역할은 exact input과 최소 권한을 가진 독립 작업으로 실행되며, output은 schema와 CLI/CI gate를 통과하기 전까지 lifecycle authority를 갖지 않는다.
- **영향 가능성이 있는 boundary, component, document 또는 operational flow:** repository-backed skills, agent delegation prompt/context, policy/schema, artifact handoff, CI, human confirmation/approval UX, governance documentation.
- **예상 compatibility, migration 또는 rollout concern:** 기존 네 skill과 adopter workflow의 호환성, Hermes 전용 기능과 provider-neutral contract의 분리, 기존 수동 운영을 강제로 agent-managed 상태로 전환하지 않는 opt-in rollout이 필요하다.
- **검토한 repository/context evidence:** `AGENTS.md`, `specbound.yaml`, `docs/governance/issue-sdlc.md`, 기존 Discovery/REQ lineage, 현재 `skills/` inventory, Hermes delegation documentation.

## 9a. Risk classification decision

`low < medium < high` 순서로 보수적으로 판정한다.

| Artifact risk | 판정 기준 |
| --- | --- |
| `low` | draft/documentation 중심이며 runtime, data, security 또는 lifecycle authority에 영향을 주지 않고 쉽게 되돌릴 수 있다. |
| `medium` | code, configuration, behavior 또는 canonical evidence를 변경하지만 영향 범위가 제한되고 복구 가능하며 security/authority/production 변경은 없다. |
| `high` | security, authentication, authorization, 데이터 손실, 되돌리기 어려운 외부 mutation, production release 또는 lifecycle authority 경계에 영향을 줄 수 있다. |

작업별 최소 Risk는 다음과 같다.

| 작업 종류 | 최소 Risk | 근거 |
| --- | --- | --- |
| Discovery 작성 | `low` | authority 없는 draft 작성 |
| REQ 작성 | `low` | authority 없는 draft 작성 |
| Micro-SPEC 작성 | `low` | implementation authority 없는 계획 작성 |
| Independent Review | `medium` | 다음 단계 판단에 영향을 주는 review 결과 생성 |
| Implementation | `medium` | code 또는 repository file mutation |
| Iteration-QC | `medium` | implementation verification evidence 생성 |
| Delivery-QC | `medium` | delivery decision evidence 생성 |
| Confirm/Approve | `high` | lifecycle authority 행사 |
| Delivery 결정 | `high` | delivery 가능 여부 결정 |
| Merge/Release | `high` | 실제 integration 또는 release 실행 |

- **Effective task risk:** `max(대상 artifact risk, 작업 종류의 최소 Risk)`로 계산한다.
- **강제 상승 조건:** security/authentication/authorization 변경, 데이터 삭제 또는 복구 곤란, lifecycle authority 행사, production release, 되돌리기 어려운 외부 mutation, 무단 implementation/delivery 가능성이 있으면 `high`로 분류한다.
- **분류 절차:** Discovery Author가 evidence와 함께 `risk_class`를 제안하고, Independent Reviewer가 근거를 검토하며, accountable confirmer가 exact Discovery snapshot의 risk를 confirmation 시 확정한다. 후속 REQ와 MS/IQC/DQC chain은 confirmed parent risk를 낮출 수 없다. 더 높은 risk가 발견되면 parent Discovery를 새 revision으로 재평가한다.
- **현재 Discovery:** `dcy-0004-r1`은 agent mutation 권한, author/reviewer 독립성, IQC/DQC 판정 및 human/CLI/CI authority 경계를 다루므로 draft에서 `risk_class: high`를 채택한다. 이 값은 exact snapshot confirmation 전까지 proposed/adopted classification이며 lifecycle상 confirmed risk가 아니다.
- **현재 enforcement 효과:** `risk_class: high`는 이 Discovery의 confirmation authority를 `specbound.yaml`의 high-risk allowlist에서 선택하게 한다. 역할 수나 모델 등급을 변경하지 않는다. Task-level risk의 machine-readable 표현과 검증은 후속 REQ에서 구체화한다.

## 9b. Risk handling rules

모든 등급에서 OQ-1의 7개 역할과 역할 분리는 유지한다. 모든 task는 exact artifact path/ID/revision/digest를 입력으로 받고, role contract가 허용한 path와 tool만 사용하며, agent verdict를 authority decision으로 취급하지 않는다. 아래 표의 행은 §9a에서 계산한 Effective task risk로 선택한다.

| Effective task risk | Task 실행 통제 | Handoff 전에 필요한 evidence | Authority-bearing transition |
| --- | --- | --- | --- |
| `low` | role별 허용 path/tool로 제한하고 candidate 변경만 수행한다. | affected scope의 targeted deterministic check와 Independent Reviewer의 별도 context verdict가 필요하다. | authority-bearing task의 최소 Risk가 `high`이므로 이 행에는 해당하지 않는다. |
| `medium` | `low` 통제에 더해 mutation은 격리된 branch/fixture/copy에서 먼저 수행하고 rollback 또는 target-absence를 검증한다. | applicable한 targeted check, negative test, affected subsystem regression test와 별도 Independent Reviewer verdict가 필요하다. | authority-bearing task의 최소 Risk가 `high`이므로 이 행에는 해당하지 않는다. |
| `high` | `medium` 통제에 더해 secret/network/production/authority-record write는 기본 거부하며 exact scope의 명시적 authorization 없이는 실행하지 않는다. | task kind에 applicable한 전체 지원 CI, failure/rollback/no-partial-mutation evidence와 별도 Independent Reviewer verdict가 필요하다. reviewer와 accountable authority는 동일한 task/session이 될 수 없다. | authority는 **Effective task risk가 아니라 target artifact의 canonical risk**로 transition별 `specbound.yaml` allowlist에서 선택하고 canonical CLI로 결정한다. confirmation, approval, delivery, merge/release를 unattended agent action으로 실행하지 않는다. |

- **Fail closed:** 필요한 evidence, allowlist authority 또는 exact binding 중 하나라도 없으면 task 결과는 `blocked`이며 다음 lifecycle transition을 요청하거나 실행하지 않는다.
- **Role invariance:** Risk는 7개 역할을 합치거나 추가하지 않는다. Risk가 높아질수록 동일한 역할의 tool 제한, evidence 깊이와 authority 분리가 강화된다.
- **Implementation boundary:** 이 절은 Discovery-level policy decision이다. machine-readable policy/schema, CLI validation 및 CI enforcement는 별도로 confirmed된 이 Discovery와 approved 후속 REQ 없이는 구현 권한을 갖지 않는다.

### 9c. Evidence applicability by task and mutation class

Effective task risk는 통제 강도를 정하지만 모든 evidence가 모든 task에 기계적으로 적용되는 것은 아니다. 후속 policy/result schema는 각 evidence slot에 `provided` 또는 `not_applicable`과 substantive reason을 요구하고, 누락되거나 허용되지 않은 `not_applicable`은 `blocked`로 처리한다.

| Task kind | Mutation class | 항상 필요한 evidence | 조건부 evidence / `not_applicable` 규칙 | Authority 처리 |
| --- | --- | --- | --- | --- |
| Read-only review | `none` | target SHA, reviewed inputs, findings, verdict, `changed_paths: []` | rollback/no-partial-mutation은 no-write 증명으로 대체한다. negative/regression/full CI는 executable behavior를 검토할 때만 필요하며 아니면 이유를 기록한 `not_applicable`이다. | verdict는 non-authorizing |
| Candidate artifact authoring | `candidate_write` | exact parent binding, schema/template check, changed path, validation | 실패 시 target absence 또는 atomic-write evidence가 필요하다. executable schema/config/validator를 바꾸지 않는 docs-only candidate의 full CI는 targeted validation으로 대체하고 이유를 기록한다. | author result는 non-authorizing |
| Repository implementation | `repository_mutation` | reviewed MS binding, changed paths, focused tests, rollback/no-partial-mutation | behavior/rejection path가 있으면 negative test와 affected regression이 필수다. `high`이면 지원 CI 전체가 필수다. | implementation result는 non-authorizing |
| IQC/DQC evidence generation | `evidence_write` | exact parent/result digests, evidence coverage, schema validation, source `changed_paths: []` | implementation code를 바꾸지 않으므로 code rollback은 `not_applicable`; canonical evidence issuance의 atomicity/target-absence evidence로 대체한다. | configured authority의 별도 canonical record 필요 |
| Confirmation/approval/review decision | `authority_transition` | exact pre/post snapshot, artifact risk, allowlist identity, substantive reason, canonical CLI result | code test와 rollback은 `not_applicable`; transition atomicity와 no-record-on-failure evidence가 필수다. | artifact risk가 allowlist selector이며 task handling은 항상 `high` |
| External/production mutation | `external_mutation` | 첫 후속 REQ에서는 없음 | 첫 후속 REQ에서 항상 `blocked`; 별도 confirmed Discovery와 approved REQ가 필요하다. | 별도 governance 필요 |

- **CI 의미:** “전체 지원 CI”는 repository executable code, schema, config 또는 validator 동작을 변경하는 high-risk handoff에 적용한다. read-only/docs-only task는 `specbound validate`, exact binding 및 해당 문서/schema check로 대체하고 `not_applicable` reason을 남긴다.
- **Negative test 의미:** 거부·실패 behavior가 있는 구현 또는 policy/schema 변경에 적용한다. 순수 read-only 검토에는 적용하지 않는다.
- **Authority selector와 task controls 분리:** target artifact risk는 allowlist를 선택하고, Effective task risk는 tool/isolation/evidence 통제를 선택한다. 둘을 서로 대체하지 않는다.
