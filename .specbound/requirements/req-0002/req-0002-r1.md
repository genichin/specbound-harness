# REQ: governed canonical REQ drafting and revision control

> **Lifecycle boundary:** This requirement is derived from the exact confirmed Discovery `dcy-0002-r1`. It is not itself an approval and does not authorize implementation, merge, delivery, or release. Any lifecycle decision must be represented by a matching canonical decision record; any material change must be expressed as a new REQ revision rather than by mutating an approved revision.

## 1. Goal

Implement a repository-local `specbound req draft` command and an accompanying repository-local authoring skill that safely create a canonical REQ draft from a confirmed Discovery. Extend deterministic validation so REQ revision latestness, supersession exceptions, and approval-binding validation are fail-closed.

## 2. Parent binding and problem statement

- **Parent Discovery:** `.specbound/discoveries/dcy-0002-r1.md`
- **Parent confirmation:** `.specbound/confirmations/dcy-0002-r1.confirmation.json`
- **Bound parent digest:** `053527951904482112bac0fad9490a267191696100148c9edf0344efc2dbf872`
- **Authorized parent action:** `draft_req_only`
- **Problem:** The current bootstrap can validate an existing approved REQ and its approval binding, but it has no canonical REQ-drafting command, REQ authoring workflow, or enforceable REQ revision/latestness policy. A manually created REQ can therefore lose deterministic lineage and revision controls before review.

## 3. Scope

### In scope

- A deterministic `specbound req draft` CLI workflow that creates only a canonical `status: draft` REQ.
- Exact parent Discovery/confirmation verification before draft issuance.
- Canonical REQ template and repository-local authoring skill for the implemented contract.
- Enforceable REQ revision and supersession policy in configuration and validation.
- Fail-closed validation of approval bindings, including revision/currentness policy where an approval record is present.
- Positive and negative fixture/test coverage, CLI documentation, and adopter-facing contract updates.

### Out of scope

- Approving a REQ, creating an approval record, or changing a REQ to `status: approved`.
- Micro-SPEC, iteration-QC, delivery-QC, merge, release, tracker, external signing, or live Hermes-profile functionality.
- Migration of pre-existing adopter REQs. This first implementation slice is explicitly greenfield-only; existing adopter repositories remain outside the adoption boundary until a later Discovery/REQ defines migration behavior.

## 4. Acceptance criteria

- **AC-001 — Parent authorization gate:** `specbound req draft <discovery-target> <requirement-target>` must accept only canonical `dcy-<id>-r<revision>` and `req-<id>-r<revision>` targets. Before any write, it must verify the exact canonical Discovery path, `status: confirmed`, a matching confirmation record, matching final SHA-256, and `permitted_next_action: draft_req_only`. Missing, unsafe, malformed, mismatched, stale, or over-broad parent evidence must return structured blockers and leave no REQ artifact behind.

- **AC-002 — Canonical, non-overwriting draft issuance:** The command must derive and write only `.specbound/requirements/req-<id>/req-<id>-r<revision>.md`, reject traversal/absolute/noncanonical paths and symlinked canonical components, and refuse to overwrite an existing artifact. The generated document must have `status: draft`, bind the verified parent Discovery path/ID/revision/final digest/confirmation path, and clearly state that draft creation is not approval or implementation authority.

- **AC-003 — Draft template and authoring skill:** A canonical REQ template and `skills/draft-req/SKILL.md` must describe the same repository-local path, lineage, status, scope/non-goal, acceptance-criteria, risk, and authority contract as the CLI/validator. The skill must require a valid confirmed Discovery, prohibit self-approval and manual approval-record issuance, and direct operators to the repository-local `.venv/bin/python -m specbound.cli` commands. Guidance must not substitute for a passing CLI/validator result.

- **AC-004 — REQ revision policy:** `specbound.yaml` must define and preflight-validate an explicit REQ revision policy. At minimum: duplicate `(requirement_id, revision)` artifacts are rejected; a new revision is immutable history rather than an in-place rewrite; a REQ approval is eligible only for the latest revision by default; and any lower-revision approval requires a structured, substantive supersession exception bound to the approving authority and timezone-bearing timestamp. The validator must not silently treat a higher numeric revision as an implicit deletion or invalidation of historical records.

- **AC-005 — Fail-closed approval-binding validation:** For every `status: approved` REQ, validation must continue to require the canonical approval record and exact path/ID/revision/SHA-256/risk/authority binding. It must additionally reject an approval that violates the REQ latestness/supersession policy, has a malformed or unauthorized exception, or disagrees with the canonical REQ status/risk/revision. A missing or invalid approval must not increment approved-REQ success counters.

- **AC-006 — Behavioral evidence:** Tests and isolated fixtures must exercise: valid draft issuance; duplicate target refusal; unconfirmed/missing/mutated/over-authorized parent rejection; unsafe canonical path or symlink rejection; newer REQ revision blocking an older approval by default; valid structured supersession exception behavior; malformed exception rejection; and approval digest mismatch. Documentation and templates must remain aligned with the executable contract. The repository-local verification contract must pass.

## 5. Design constraints and decisions

1. **Single canonical owner:** REQ source is canonical only under `.specbound/requirements/`; control-plane records remain under `.specbound/`. No synchronized duplicate approval or tracker state is introduced.
2. **Narrow authority:** A confirmed Discovery authorizes draft creation only. The draft command must not issue approval evidence or infer approval from a user/agent invocation.
3. **Minimum necessary binding:** Draft creation binds to the parent confirmed Discovery's final exact bytes and confirmation path. Downstream approval binds the exact REQ bytes; it does not need to rebind every historical artifact.
4. **Revision semantics:** A material requirement/scope/risk/acceptance change requires a new numeric REQ revision. Existing approved revisions are never edited to repair a digest mismatch.
5. **Exception semantics:** A supersession exception is auditable disclosure for a non-latest approval; it is not an automatic authority expansion, deletion of later revisions, or authorization for implementation/merge/release.
6. **Adoption boundary:** Absence of future Micro-SPEC/QC records remains valid until a separately approved adopted scope requires them.
