# Micro-SPEC — REQ-0004 slice 001: provider-neutral role policy and agent-result contract

> **Lifecycle boundary:** 이 planning artifact는 exact approved `req-0004-r1` snapshot의 `CG-1`인 AC-001과 AC-003에만 binding된다. 별도의 exact digest-bound `approved_for_implementation` Micro-SPEC review decision 전에는 구현할 수 없다. 이 문서와 향후 agent result는 confirmation, REQ approval, Micro-SPEC review decision, iteration-QC verification, delivery decision, Merge 또는 Release authority가 아니다.

## Objective

정확히 7개의 stable lifecycle role ID와 역할별 최소 권한을 표현하는 provider-neutral `agent-roles` policy 및 schema를 정의하고, 모든 역할이 공통으로 반환할 exact-bound `agent-result` schema와 deterministic core validator를 구현한다. Root validation은 policy의 누락·중복·unknown role, unsafe path/tool/mutation/output/claim을 fail-closed하게 거부한다. 실행 전 role-request validation은 repository에서 exact target과 current lifecycle state를 다시 읽어 declarative eligibility를 확인하고, result validation은 target identity/digest, execution/context identity, provenance, mutation, evidence applicability, verdict와 permitted next action의 closed structure 및 role-policy 정렬을 검증한다. 어떤 valid request/result도 canonical lifecycle state나 authority record를 직접 변경하지 않는다.

## Scope

- `.specbound/policies/agent-roles.yaml`에 다음 정확한 7개 role ID를 하나씩 정의한다: `discovery-author`, `requirement-author`, `micro-spec-author`, `independent-reviewer`, `implementation`, `iteration-qc`, `delivery-qc`.
- `schemas/agent-roles.schema.json`은 policy envelope, 정확한 role inventory, required input 종류, allowed path/tool category, mutation class, output kind, forbidden action/claim, declarative lifecycle eligibility, role별 `producer_result_ref`/`reviewer_run_ref`의 `required|optional|forbidden` 조건 및 evidence slot별 `required|optional`/`not_applicable_allowed` 규칙의 closed shape를 검증한다. Provider, vendor, Hermes tool/API 또는 profile 이름은 core policy에 허용하지 않는다.
- `schemas/agent-result.schema.json`은 최소한 `schema_version`, `role_id`, `execution_id`, `context_id`, `model_alias`, exact target `{path,id,revision,sha256}`, explicit nullable `producer_result_ref`와 `reviewer_run_ref`, non-authorizing `authority_type`/`authority_action_id`, `context_provenance`, target/effective risk fields, mutation class, `changed_paths`, evidence applicability entries, `pass|rework|blocked` verdict, findings 및 permitted next action을 검증한다. Micro-SPEC처럼 revision이 없는 target은 임의 revision을 만들지 않고 `revision: null`을 사용한다. Unknown field, invalid enum, absolute/traversal path와 malformed digest를 거부한다.
- Result reference는 null 또는 closed `{result_id, role_id, execution_id, context_id, sha256}` object다. `context_provenance`는 closed `{fresh_context, producer_transcript_inherited, session_memory_inherited, input_artifacts}`이며, 각 input artifact는 exact `{path,id,revision,sha256}` reference다. Evidence entry는 closed `{slot,status,artifacts,commands,reason}`이고 `status`는 `provided|not_applicable`만 허용한다. `provided`에는 non-empty artifact/command evidence와 `reason: null`이 필요하고, `not_applicable`에는 빈 evidence와 substantive reason이 필요하다. Policy가 해당 role/task/mutation slot에 `not_applicable_allowed`를 선언하지 않으면 core validator가 거부한다.
- `src/specbound/agent_contract.py`에 `load_agent_roles_policy`, `validate_agent_roles_policy`, `validate_role_request`, `validate_agent_result`, exact target binding/path/result-policy alignment helper와 structured blocker 생성을 캡슐화한다. `validate_role_request`는 caller가 주장한 state를 신뢰하지 않고 exact repository target 및 기존 canonical record에서 current state를 다시 도출한 뒤 role policy eligibility, requested path/tool/mutation/output/action을 실행·candidate publication 전에 검사한다. 이 모듈은 Hermes 없이 호출 가능해야 하며 canonical record writer나 delegation runtime을 포함하지 않는다.
- `src/specbound/cli.py`는 read-only `specbound agent check-role-request --request-file REQUEST.json`와 `specbound agent validate-result --result-file RESULT.json` surface를 제공한다. 두 명령은 성공/structured blocker만 반환하고 candidate, canonical artifact 또는 authority record를 쓰지 않는다.
- `src/specbound/validation.py`와 `specbound.yaml`은 versioned opt-in `policy.agent_contract.{enabled,roles_path}`를 통해 이 저장소에서 root `specbound validate`가 repository-owned role policy를 검사하도록 연결한다. `enabled: false` 또는 설정 부재인 adopter는 기존 manual lifecycle validation을 유지하며 agent request/result를 valid로 간주하지 않는다. `templates/specbound.yaml`과 valid/invalid fixture config도 같은 provider-neutral opt-in 경계를 검증한다.
- `tests/test_agent_contract.py`와 `fixtures/agent-contract/`에 7-role positive inventory, role별 forbidden path/tool/mutation/output/claim, missing/duplicate/unknown role, malformed/extra field, absolute/traversal path, exact SHA mismatch, invalid changed path, missing evidence, unknown verdict/action, policy-result conflict 및 no-canonical-mutation cases를 추가한다. 별도로 exact current state와 맞지 않는 role request, caller state spoofing, policy가 허용하지 않은 evidence `not_applicable`, role별 required/forbidden result reference 및 malformed provenance를 명시적으로 거부한다.
- Schema/fixture packaging 및 installed-wheel validation이 필요한 경우 `pyproject.toml`, `.github/workflows/ci.yml` 또는 package-data configuration을 최소 범위로 조정하되, source checkout과 installed CLI가 동일한 core contract를 검증해야 한다.

### Provider-neutral role boundary

- Author 역할 3개는 자신의 candidate family만 작성할 수 있고 confirmation, approval, review decision, QC verification 또는 다음-stage artifact를 발행할 수 없다.
- `independent-reviewer`는 read-only이며 `changed_paths: []`만 허용한다.
- `implementation`은 reviewed Micro-SPEC이 전달한 source scope만 후보 mutation으로 표현하며 canonical lifecycle/evidence/authority root를 변경할 수 없다.
- `iteration-qc`와 `delivery-qc`는 각각 자신의 candidate evidence family만 표현하고 implementation source, approval, delivery decision 또는 Merge/Release를 변경하거나 주장할 수 없다.
- 모든 역할의 canonical output은 non-authorizing `agent-result`이며 `authority_type: none`, `authority_action_id: null`을 유지한다. Authority-bearing transition은 이 slice의 output/action registry에 포함하지 않는다.

## Non-goals

- AC-002의 7개 repository-backed `SKILL.md` 작성 또는 policy-to-skill alignment는 `ms-0004-003`으로 defer한다.
- AC-004~AC-006의 cross-result producer/reviewer/QC identity-overlap matrix, Effective Task Risk **계산**, risk별 evidence applicability matrix, 전체 canonical lifecycle graph 및 transition-specific authority selector 집행은 `ms-0004-002`로 defer한다. 그러나 AC-001/AC-003에 필요한 exact current-state role-request 차단, closed reference/provenance/evidence shape, policy-declared role별 nullability, evidence slot 및 `not_applicable` 허용 여부의 최소 fail-closed 집행은 이 slice에서 완료한다.
- AC-007/AC-008의 Hermes delegation, role-to-skill/tool/workdir mapping, runtime result normalization, unsupported Delivery/Merge/Release request guard는 `ms-0004-004`로 defer한다.
- AC-009/AC-010의 전체 통합 CI, final rollback evidence, repository-wide guidance와 opt-in rollout 완료는 `ms-0004-005`로 defer한다.
- 다음 역할 자동 선택, multi-role chain, retry/loop/scheduler, multi-model/profile routing, live Hermes profile/config 변경, secret/network/production mutation 및 external policy engine은 구현하지 않는다.
- approved `req-0004-r1`, approval/review/confirmation record, 기존 canonical lifecycle artifact와 `policy.control_plane_adoption`을 수정하지 않는다.

## Baseline

`req-0004-r1`은 `repository-maintainer` authority의 `.specbound/approvals/req-0004-r1.approval.json`이 SHA-256 `495c04dc6c1f7b726ea7f654477bdc065c4ca67f2e5dd82797b7ad3fc723675a`에 binding한 high-risk approved REQ다. 현재 저장소에는 canonical lifecycle path/binding validator, JSON schema examples, four repository-backed lifecycle skills와 append-only review/approval writers가 있으나, agent-role policy, agent-result schema, role/result validator 및 제안된 7개 역할 contract는 존재하지 않는다. `pyproject.toml`은 현재 PyYAML만 runtime dependency로 사용하며 existing schemas는 주로 repository contract artifact이고 agent result를 검증하는 runtime API는 없다.

현재 구현된 7-role Independent Reviewer contract는 없으므로 이 Micro-SPEC의 작성·검토를 그 future contract가 수행했다고 주장하지 않는다. 구현 전 검토는 기존 governance의 별도 fresh context에서 수행하는 **Bootstrap advisory review**와, high-risk allowlist의 `independent-advanced-llm-reviewer`가 별도로 발행하는 canonical Micro-SPEC review decision으로 구분한다.

## Verification plan

- `tests/test_agent_contract.py`에서 policy schema와 semantic inventory를 직접 검증한다. 정확히 7개 role이 한 번씩 존재하는 positive fixture와 missing/duplicate/unknown role, runtime-specific field, widened path/tool/mutation/output/authority claim negative fixture를 실행한다.
- 각 역할마다 허용 candidate path와 최소 하나 이상의 forbidden canonical/authority/external path를 검증하고, absolute path, `..` traversal, separator/normalization near-miss 및 symlink/containment 경계를 fail-closed하게 검사한다.
- Agent-result valid fixture는 exact target bytes의 SHA-256을 재계산하고 role policy와 정렬된 mutation/output/verdict/action을 통과시킨다. stale/mismatched digest, missing/extra identity, unknown verdict/action, non-empty reviewer `changed_paths`, role별 required/forbidden reference 위반, transcript/session inheritance provenance, invalid evidence envelope, policy가 허용하지 않은 `not_applicable`과 authority claim은 distinct blocker를 반환한다.
- Role-request fixture는 repository의 exact target/current state를 validator가 직접 도출했을 때만 eligible role을 통과시킨다. current-state-ineligible role, caller state spoofing, stale target digest, forbidden requested path/tool/mutation/output/action은 실행·candidate publication 전 distinct blocker로 거부한다.
- 모든 negative result validation 전후에 target artifact, lifecycle record roots와 `specbound.yaml`의 SHA-256을 비교하여 no-canonical-mutation을 증명한다.
- Windows에서는 platform-neutral focused schema/semantic tests와 `specbound preflight`, `specbound validate`, docs check, `git diff --check`를 실행한다. POSIX path/symlink/atomic behavior를 포함한 full suite는 GitHub Actions Ubuntu의 Python 3.11·3.12에서 실행한다.
- 최종 지원 CI는 `python -m pytest`, `specbound preflight`, `specbound validate`, `specbound docs requirements --check`, wheel build 및 installed-wheel validation을 통과해야 한다.

## QC exit rule

이 slice는 다음이 모두 충족될 때만 Iteration-QC 후보를 요청할 수 있다: exact approved parent와 reviewed Micro-SPEC binding 유지, 7-role policy inventory의 positive/negative matrix 통과, current-state-ineligible role-request의 pre-execution 차단, valid/invalid agent-result matrix 통과, role별 reference/provenance/evidence 조건과 unauthorized `not_applicable` 차단, forbidden authority/runtime-specific claim의 zero-mutation 증명, provider-neutral core의 Hermes-free 실행, 지원 Ubuntu Python 3.11·3.12 전체 CI 통과. AC-004~AC-006의 cross-result identity/risk/full lifecycle semantics 또는 7개 role skill/Hermes adapter가 아직 없음을 명시해야 하며, 이 slice 결과만으로 실제 agent invocation이나 canonical transition이 허용됐다고 주장할 수 없다.

하나라도 실패하면 verdict는 `rework` 또는 `blocked`이며 `permitted_next_action`은 implementation 확대나 다음 Micro-SPEC 자동 작성이 될 수 없다. 특히 role inventory, exact digest, path containment, authority claim 또는 result-policy alignment 실패는 fail-closed blocker다.

## Rollback and containment

구현 시작 전에 planned changed-path와 기존 파일 SHA-256을 기록한다. 이 high-risk slice가 validation regression, policy over-permission, partial write 또는 packaging failure를 만들면 신규 `.specbound/policies/agent-roles.yaml`, 두 agent schema, `src/specbound/agent_contract.py`, agent fixture/test/template를 제거하고, 실제로 수정한 `src/specbound/validation.py`, `src/specbound/cli.py`, `specbound.yaml`, `templates/specbound.yaml`, fixture config, `pyproject.toml`, package-data 및 `.github/workflows/ci.yml`을 모두 exact pre-implementation baseline으로 되돌린다. 그 뒤 source checkout과 installed-wheel의 config/schema/validator 동등성, 기존 manual lifecycle CLI, full supported CI 및 canonical artifact digest 불변을 재검증한다.

Approved REQ/approval bytes, 기존 canonical evidence, `policy.control_plane_adoption`과 live Hermes profile은 rollback 대상으로 변경하지 않는다. Invalid request/result/policy 검증은 read-only이고 candidate, canonical artifact나 authority record를 생성하지 않아야 한다. 격리 fixture 밖 mutation, external/network/secret write 또는 authority record write가 관찰되면 즉시 `blocked`로 처리하고 해당 실행을 폐기한다.
