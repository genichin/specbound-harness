# Micro-SPEC — REQ-0003 slice 002: issuance-request prevalidation boundary

> **Lifecycle boundary:** 이 planning artifact는 exact approved `req-0003-r2`의 AC-001과 AC-002에만 binding된다. 자체로는 approval, iteration-QC, delivery-QC, adoption, merge, delivery, release 또는 implementation-start authority가 아니다. High-risk parent이므로 append-only `micro-spec review-decision`의 exact `approved_for_implementation` verdict가 있어야 해당 bounded slice만 implementation 및 후속 iteration-QC를 시작할 수 있다.

## Objective

`micro-spec`, `iteration-qc`, `delivery-qc` 중 하나를 명시적으로 선택하는 canonical issuance-request interface의 read-only pre-publication boundary를 정의·구현한다. 이 slice는 candidate content, target identity, configured roots와 family-specific parent precondition을 mutation 전에 fail-closed로 평가하고, rejection은 structured blocker 및 requested-target absence로 관찰 가능해야 한다.

## Scope

- `specbound` CLI에 artifact kind, canonical target identity, complete candidate content를 모두 요구하는 하나의 explicit issuance-request surface를 추가한다.
- caller-supplied filesystem path 대신 configured root와 kind/identifier에서 canonical safe-relative target을 도출한다.
- unknown kind, malformed/ambiguous identifier, absolute/traversal/alias path, incomplete candidate, schema·semantic-invalid candidate, missing/stale/mismatched parent, unmet family prerequisite를 write attempt 전에 structured blocker로 reject한다.
- candidate validation, target binding, parent identity/path/revision/digest checks와 family dispatch를 read-only helper로 분리한다.
- CLI help, template, authoring guidance 및 copied-fixture tests를 issuance request가 non-authorizing control임을 명시하도록 맞춘다.

## Non-goals

- canonical artifact publication, exclusive create, race handling, fsync, digest result reporting, rollback cleanup 또는 overwrite/duplicate behavior(AC-005~AC-007).
- AC-003 pre-adoption Micro-SPEC publication, AC-004 adopted QC parent-graph behavior, AC-008 full behavioral matrix.
- production `specbound.yaml` adoption registry, approved REQ/approval bytes, historical review/rejection/reconsideration evidence 또는 live Hermes profile 변경.
- approval, confirmation, adoption, merge, delivery 또는 release authority issuance.
- `ms-0003-001`의 independent-review blocker를 해소·변경하거나 그 implementation을 시작하는 일.

## Baseline

`req-0003-r2`는 high-risk approved REQ이며 approval record의 exact SHA-256 `e8e3833e7e1b559bd0ed862cfd13b95a7fd2aadce92b89a9aac8df6b135fc354`에 binding된다. 현재 canonical validator는 existing artifact topology를 read-side로 평가하지만 candidate issuance request의 pre-publication CLI surface는 제공하지 않는다. Production adoption registry는 pre-adoption empty state를 유지해야 한다.

## Verification plan

- copied temporary fixture에서 real CLI를 호출하여 each supported kind의 explicit parsing, canonical target derivation 및 complete candidate requirement를 확인한다.
- unknown kind, malformed/missing/ambiguous identity, absolute/traversal/alias target, incomplete/invalid candidate, invalid parent evidence 및 unsupported/deferred family precondition마다 stable blocker code/path/detail과 requested-target absence를 assert한다.
- all rejection paths에서 fixture target digest/entry가 생성 또는 변경되지 않음을 assert한다.
- help/template/guidance에 issuance non-authority wording이 존재함을 contract assertion으로 확인한다.
- focused fixture tests, `.venv/bin/python -m pytest -q`, `.venv/bin/python -m specbound.cli preflight`, `.venv/bin/python -m specbound.cli validate`, `git diff --check`를 실행한다.
- production adoption registry가 empty이며 r2 REQ 및 approval binding SHA-256이 unchanged임을 재계산한다.

## QC exit rule

selected AC-001/AC-002에 대한 copied-fixture positive and negative CLI evidence가 모두 pass하고, every rejection proves target absence, full suite 및 root preflight/validate가 pass하며, adoption registry와 historical evidence bytes가 unchanged일 때만 `verified` iteration-QC를 요청할 수 있다. 이 계획 artifact 또는 그 tests만으로 AC-003~AC-008, publication, adoption, implementation, merge, delivery 또는 release completion을 주장해서는 안 된다.

## Rollback and containment

unsafe target acceptance, prevalidation 후 write residue, parent-digest bypass 또는 authority leakage가 관찰되면 issuance-request command path를 reject-only 상태로 되돌리고 copied fixture와 failed command output을 보존한다. Cleanup은 current invocation이 만든 temporary fixture target만 제거할 수 있으며, production registry, approved REQ/approval, historical review artifacts, existing Micro-SPEC 또는 live Hermes profile은 변경·삭제·rollback 대상으로 삼지 않는다.
