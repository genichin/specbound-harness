# Micro-SPEC — REQ-0005 slice 001: authority-bound adoption records and derived effective state

> **Lifecycle boundary:** 이 planning artifact는 exact approved `req-0005-r1` snapshot의 CG-1인 AC-001과 AC-002에만 binding된다. Candidate authoring과 Bootstrap advisory review는 authority가 아니다. High-risk parent의 canonical `micro-spec review-decision`이 이 exact Micro-SPEC SHA-256에 `approved_for_implementation`을 기록하기 전에는 구현을 시작할 수 없다. 그 결정도 이 slice의 구현만 허용하며 operational adoption, canary 실행, activation, canonical IQC/DQC publication, Delivery, Merge, Release 또는 rollout을 허용하지 않는다.

## Objective

Append-only adoption/canary-outcome/activation record contract와 deterministic effective-state oracle을 정의하고, exact approved non-completed canary REQ와 하나의 `iteration_qc|delivery_qc` transition만 대상으로 하는 distinct canonical adoption writer를 구현한다. Writer와 resolver는 authority, policy, Git ancestry/timestamp, freshness attestation, prior-work absence, stage order, exception/outcome/closeout history를 fail closed하게 검증하며, `specbound.yaml`의 수동 per-REQ 목록이나 generated projection을 authority로 사용하지 않는다.

## Scope

### 1. Canonical topology와 strict record contracts

- `specbound.yaml`, `templates/specbound.yaml`, `fixtures/valid-minimal/specbound.yaml`, `src/specbound/validation.py`의 canonical contract에 다음 exact roots/patterns를 추가한다.
  - adoption decision: `.specbound/adoptions/req-{numeric-id}/adp-{numeric-id}-r{positive-revision}-{transition}.json`
  - canary outcome: `.specbound/canary-outcomes/req-{numeric-id}/cny-{numeric-id}-r{positive-revision}-{transition}-a{positive-sequence}.json`
  - activation decision: `.specbound/activations/req-{numeric-id}/act-{numeric-id}-r{positive-revision}-{transition}.json`
  - `{transition}`은 exact enum `iteration_qc|delivery_qc`, `{positive-sequence}`는 1 이상의 정수다.
- `schemas/adoption-decision.schema.json`, `schemas/canary-outcome.schema.json`, `schemas/activation-decision.schema.json`과 exact-byte packaged mirrors `src/specbound/schemas/adoption-decision.schema.json`, `src/specbound/schemas/canary-outcome.schema.json`, `src/specbound/schemas/activation-decision.schema.json`, 그리고 대응하는 `templates/adoption-decision.json`, `templates/canary-outcome.json`, `templates/activation-decision.json`을 추가한다. 모든 schema는 `additionalProperties: false`, exact path/ID/revision/transition coupling, lowercase SHA-256, full Git object ID, UTC RFC3339 timestamp, non-placeholder action/context와 아래 family별 closed field/enum을 요구한다. `reason`은 adoption decision 전용 required field이며 canary-outcome과 activation에서는 금지한다. Canonical bytes는 UTF-8 without BOM, LF, lexicographically sorted object keys, two-space indentation, `ensure_ascii: false`, exactly one trailing LF인 Python `json.dumps(..., sort_keys=True, indent=2, ensure_ascii=False) + "\n"` 결과다.
- Adoption schema는 AC-001의 exact approved REQ binding, `scope_mode: exact_canary`, transition, risk, authority, `authority_action_id`, `context_id`, exact `decision: adopted_for_exact_canary`, reason, writer timestamp, exact `permitted_next_action: approve_bootstrap_exception_for_exact_canary`, full `adoption_source_commit`, stage-specific full `canary_capability_baseline_commit`, writer-derived `canary_capability_baseline_at`, `canary_work_state: not_started`, same-authority `canary_work_attested_by`, non-late `canary_work_attested_at`, sorted non-empty `canary_work_source_refs`, 그리고 `{path, sha256, selector}` policy binding을 모두 요구한다. 이 decision/next-action pair 외 조합은 거부한다. IQC와 DQC adoption은 filename, transition, action/context와 record identity가 각각 독립이어야 한다.
- Source ref는 exact closed union으로 표현한다: repository ref는 `{kind: repository, path, sha256}`, external ref는 `{kind: external, id, digest_algorithm: sha256, digest}`만 허용한다. 모든 string은 Unicode NFC여야 한다. Repository ref key는 `(0, path, sha256)`, external ref key는 `(1, id, "sha256", digest)`이며 각 tuple component를 Unicode code-point lexicographic order로 비교해 오름차순 정렬하고 exact tuple equality를 duplicate로 거부한다. Repository path는 safe-relative canonical spelling이어야 하고 digest는 frozen `adoption_source_commit` tree의 exact blob bytes에서 재계산한다. External ref는 network dereference 없이 non-placeholder immutable ID와 lowercase SHA-256 attestation만 검증한다.
- Canary-outcome schema는 exact adoption path/SHA, 당시 active exception path/pre-close SHA-256/그 bytes를 포함하는 `pre_close_commit`, same transition, `scope_mode: exact_canary`, positive attempt sequence, exact `outcome: passed|failed`, authority, `authority_action_id`, `context_id`, writer timestamp만 bind한다. `reason`, `decision`, `permitted_next_action`, self path/SHA, `passed_outcome_commit`, closed exception, closeout 또는 prospective-baseline field는 허용하지 않는다. Outcome 자체는 closeout·activation·matrix update authority가 아니다.
- Activation schema는 exact adoption path/SHA, exact successful outcome path/SHA, 그 outcome bytes와 bound active pre-close exception bytes를 보존한 `passed_outcome_commit`, transition, `scope_mode: prospective_after_baseline`, pre-activation `prospective_baseline_commit`과 writer-derived `prospective_baseline_at`, active exception path/pre-close SHA/commit, 같은 path의 closed exception SHA와 `closeout_commit`, exact ledger path/SHA binding, activation selector에 대한 `{path, sha256, selector}` policy binding, authority, `authority_action_id`, `context_id`, exact `decision: activated_for_prospective_scope`, writer timestamp를 bind한다. `reason`과 `permitted_next_action`은 schema에 없으며 activation만으로 matrix update나 QC publication을 authorize하지 않는다. 이 slice는 canary/activation writer를 만들지 않지만 copied Git fixture의 strict read-side validation과 effective-state derivation이 해당 records를 검증할 수 있어야 한다.

### 3. Deterministic Git-bound resolver

- 새 `src/specbound/control_plane_adoption.py`에 strict loaders, Git object/tree/ancestry/timestamp adapter, adoption eligibility resolver, activation validity resolver와 path-sorted effective registry reconstruction을 둔다. V1 Git contract는 `git rev-parse --show-object-format`이 exact `sha1`인 repository의 full lowercase 40-hex object만 지원한다. 다른 object format, shallow repository, missing object 또는 ambiguous revision은 stable blocker로 mutation 전에 거부한다. Git 조회는 argument-list subprocess 호출을 사용하고 caller-provided timestamps나 checkout-only bytes를 신뢰하지 않는다.
- Adoption eligibility는 record의 immutable `adoption_source_commit` tree에서 고정한다. Stage-specific capability baseline이 adoption source의 ancestor인지, baseline committer timestamp를 UTC RFC3339로 정규화한 값이 record와 같은지, REQ/approval path가 baseline과 모든 ancestor에 없고 `(baseline, adoption_source]`에서 처음 도입되었는지, introduction commit timestamp와 valid `approved_at`이 baseline timestamp보다 모두 늦은지 검증한다.
- Frozen adoption-source tree와 capability-baseline 이후 source까지의 모든 ancestry commit에서 exact candidate를 bind하는 requirement/approval, Micro-SPEC, Micro-SPEC review, IQC, DQC, adoption, canary attempt/outcome, activation, active·closed Bootstrap exception/ledger/action evidence를 closed canonical root/path/identity/authority-action/context inventory로 검사한다. 과거 commit에 존재했다 삭제된 same-target evidence도 prior work다. Freshness attestation/source refs가 prior manual/Bootstrap work를 나타내거나 inventory와 모순되면 `non-completed` eligibility를 거부한다.
- IQC transition은 prior IQC/DQC/canary/activation identity가 전혀 없어야 한다. DQC transition은 exact successful IQC activation만 허용하고 prior DQC/canary/activation identity를 거부한다. IQC adoption을 DQC에서 재사용하지 않는다.
- Activation validity는 `pre_close_commit`이 `passed_outcome_commit`의 strict ancestor이고, `passed_outcome_commit`이 `closeout_commit`의 strict ancestor이며, `closeout_commit`은 `prospective_baseline_commit`과 같거나 그 ancestor인지 검증한다. 각 commit tree의 same-path active exception, exact passed outcome, same-path closed exception 및 ledger-update bytes도 검증한다. Sibling/copied outcome, failed/missing outcome, active/unclosed/mismatched exception, policy digest/selector mismatch, non-allowlisted authority 또는 `authority_action_id`/`context_id` overlap은 affected transition을 fail closed한다. 동일 allowlisted authority identity가 fresh action/context로 서로 다른 결정을 수행하는 것은 허용한다.
- Effective registry는 모든 canonical record를 repository-relative path order로 읽되 timestamp/file-order last-writer-wins를 사용하지 않는다. Invalid, duplicate exact key, same-transition multiple activation 또는 conflicting record가 있으면 stable blocker로 affected key/transition 전체를 거부한다. 각 REQ revision은 독립 판정하며 generated projection을 삭제·재생성해도 결과가 같아야 한다.
- `preflight`는 config/root/alias shape만 검사한다. Ordinary `specbound validate`는 세 canonical record family 전체의 schema, semantic, duplicate/conflict와 Git object availability를 global blocker로 검사하고, `validate --claim`과 `adoption check/list`는 같은 oracle에서 affected exact key/transition의 applicability와 stable blocker를 보고한다. Post-baseline omission이나 projection 부재는 authority를 만들지 않는다.
- `prospective_after_baseline`은 exact approval path가 activation baseline tree에 없고 valid `approved_at`이 `prospective_baseline_at`보다 늦은 revision만 포함한다. Activation baseline은 이미 고정된 canary eligibility를 소급 생성하거나 변경하지 않는다.

### 4. Distinct adoption writer와 read-only surfaces

## Rollback and containment

- Implementation defect가 발견되면 adoption CLI/parser와 derived claim applicability를 fail-closed disabled 상태로 되돌리고, failing copied-Git fixture와 blocker evidence를 보존한다. Writer rollback은 자신이 exclusive-create한 exact adoption leaf만 제거하며 pre-existing/symlink-swapped winner나 다른 canonical root를 삭제하지 않는다.
- `specbound.yaml`, template/fixture topology와 resolver를 함께 rollback하여 manual list와 derived registry가 혼합된 authority 상태를 남기지 않는다. Rollback 전후 root validation과 historical compatibility fixture를 실행한다.
- Approved `req-0005-r1`, approval/review history, transition policy, existing Micro-SPEC/IQC/DQC/Bootstrap evidence와 live Hermes profile은 immutable containment boundary이며 수정·삭제·retrospective relabel 대상이 아니다.
- 실제 live adoption/canary/activation/QC record가 생성되었거나 active exception ledger/matrix가 바뀌면 즉시 중단하고 해당 bytes와 command evidence를 보존한다. 그것은 이 Micro-SPEC의 rollback 권한으로 정리할 수 있는 정상 구현 변경이 아니라 scope/authority incident다.
