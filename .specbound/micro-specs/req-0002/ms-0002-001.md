# Manual bootstrap Micro-SPEC: guarded canonical REQ draft issuance

## 1. Parent binding and iteration objective

This manual-bootstrap Micro-SPEC derives only from the exact approved `req-0002-r1` snapshot above. It covers **AC-001** and **AC-002** only.

**Objective:** establish a deterministic `specbound req draft` operation that verifies a narrowly authorized confirmed Discovery before it writes one non-overwritable canonical REQ draft, and that fails closed without leaving a draft behind on invalid input.

## 2. Scope

### Included

- Parse only exact `dcy-<id>-r<revision>` parent and `req-<id>-r<revision>` target identifiers.
- Before writing, verify the parent canonical Discovery path, `confirmed` status, matching canonical confirmation record, parent identity/revision/risk, exact final SHA-256, and `permitted_next_action: draft_req_only`.
- Refuse missing, malformed, unsafe, stale, mismatched, symlinked, or over-authorized parent evidence with structured CLI blockers and no target artifact.
- Derive only `.specbound/requirements/req-<id>/req-<id>-r<revision>.md`; reject traversal, absolute, noncanonical, symlinked, and existing-target cases.
- Write a draft-only REQ that binds the verified parent path, ID, revision, final digest, and confirmation path, and says that drafting is not approval or implementation authority.
- Focused tests for the valid issuance path, duplicate refusal, and invalid parent evidence variants.

### Explicitly excluded

- REQ approval/rejection behavior or changes to approval-record schema/policy.
- REQ revision/latestness and supersession behavior beyond preserving the generated target's declared revision.
- Authoring-skill, README, template-wide, or adopter-contract work beyond text necessary in the generated draft to satisfy AC-002.
- Micro-SPEC lifecycle automation, iteration-QC, delivery-QC, merge, release, external signing, live Hermes-profile work, or migration of existing adopters.
- Any acceptance criterion other than AC-001 and AC-002.

## 3. Baseline and dependencies

- Parent approval: `.specbound/approvals/req-0002-r1.approval.json`, bound to the parent SHA-256 shown in frontmatter.
- Current root lifecycle validation: `specbound validate` reports `valid: true`, `approved_requirements: 1`, and no blockers.
- Current full suite baseline: `.venv/bin/python -m pytest -q` reports 35 passing tests.
- The repository already contains the `req draft` parser/dispatch and draft-validation code paths; this iteration may change only what is required to meet the selected AC behavior and its focused evidence.
- Existing unrelated working-tree changes are not evidence for this Micro-SPEC and must not be expanded or silently absorbed by its implementation.

## 4. Design and control flow

1. The CLI accepts a parent target and destination target as identifiers, never arbitrary filesystem paths.
2. It resolves both through the configured canonical topology and rejects unsafe or noncanonical forms before a write is attempted.
3. It validates the exact confirmed parent and narrow `draft_req_only` authorization, including its content digest, before creating any target directories or files.
4. It uses non-overwriting creation semantics. A pre-existing target is a structured failure, not an update path.
5. Only after all gates pass, it emits the canonical draft REQ with exact parent bindings and `status: draft`.
6. A failure at any preceding gate leaves no newly created canonical REQ artifact.

The implementation may touch `src/specbound/cli.py`, `src/specbound/validation.py`, and focused `tests/test_cli.py` coverage. Any additional file must be justified against AC-001/AC-002 in the implementation evidence.

## 5. Verification plan and retained evidence

Run from the repository root with the repository-local interpreter:

```bash
.venv/bin/python -m pytest -q tests/test_cli.py -k 'req_draft'
.venv/bin/python -m pytest -q
.venv/bin/python -m specbound.cli preflight
.venv/bin/python -m specbound.cli validate
git diff --check
```

Focused evidence must show:

- a valid confirmed parent creates exactly one canonical `status: draft` target with the expected parent bindings;
- an existing target is refused without overwriting it;
- invalid parent evidence is rejected with structured blockers and creates no target;
- a representative unsafe/noncanonical target is rejected before writing.

Do not run a successful `req draft` command against the canonical repository root when it would create an unplanned production artifact. Use an isolated temporary/copied fixture for command-level success evidence.

## 6. QC / exit rule

- **verified:** all selected AC-001/AC-002 behaviors have focused, reproducible evidence; the full suite, preflight, root validation, and whitespace check pass; no scope expansion is present.
- **rework:** a failure is confined to this objective, selected ACs, and stated boundaries; repair it and rerun focused evidence.
- **blocked:** parent approval/validation becomes invalid, a safe fixture cannot exercise the command, or required behavior needs an AC-003+ change. Record the blocker and do not implement beyond this Micro-SPEC.
- **escalate to new REQ revision:** any change to REQ scope, acceptance criteria, risk, or non-goals is required.
