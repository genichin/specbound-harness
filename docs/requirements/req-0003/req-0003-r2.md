# REQ: canonical evidence issuance 및 immutable-write safety r2

> **Revision boundary:** `req-0003-r1`과 그 approval record는 historical approved evidence로 보존한다. 이 `r2`는 r1의 issuance intent를 변경하지 않고, review 가능한 AC completion contract와 canonical draft handoff를 명시하는 successor draft다. r2 draft issuance는 review, approval, implementation, adoption, merge, delivery 또는 release authority가 아니다.

> **Lifecycle boundary:** 이 artifact의 lifecycle state는 frontmatter와 이에 대응하는 content-addressed decision record로만 결정된다. `draft` REQ는 `specbound req check-readiness req-0003-r2`를 통과한 뒤 `specbound req to-in-review req-0003-r2`로만 제출한다. 이 transition은 exact digest-bound, non-authorizing review-submission record를 만들 뿐 approval 또는 downstream authority를 만들지 않는다.

## 목표 (Goal)

isolated greenfield 또는 copied fixture repository에서만, 명시적으로 선택된 canonical evidence artifact 하나를 모든 precondition 검증 뒤 atomic exclusive publish하는 repository-local issuance interface를 정의한다. 성공은 canonical safe-relative path와 exact SHA-256으로 관찰 가능해야 하며, reject 또는 controlled write failure는 requested target을 남기지 않아야 한다.

## Scope (범위)

- `micro-spec`, `iteration-qc`, `delivery-qc` artifact family를 위한 하나의 explicit artifact-kind-selected issuance operation.
- candidate schema/semantic/parent/adoption/path validation을 mutation 전에 수행하는 fail-closed control.
- safe-relative containment, no-overwrite, same-host/local-filesystem atomic exclusive publication, ownership-safe cleanup, structured result와 final digest evidence.
- copied fixture에서만 mutation behavior를 증명하는 CLI, template, guidance, regression coverage.

## Non-goals (비목표)

- `req-0003-r1`, its approval record, existing/manual-bootstrap artifact, 또는 production adoption registry의 수정·migration·enrollment.
- approval/confirmation/rejection/adoption/merge/delivery-decision/release record의 생성 또는 변경.
- automatic target numbering, batch issuance, overwrite/replace/delete/retry-by-mutation, distributed or network-filesystem concurrency guarantee.
- live adoption, live Hermes profile rollout, implementation approval, merge, delivery 또는 release.

## Acceptance criteria

> **AC completion contract:** 각 AC의 field는 review 전에 실제 evidence contract로 채워진다. shared completion group은 group 전체가 충족되기 전 implementation-ready claim을 만들지 않는다.

### AC-001 — explicit canonical issuance request

- `observable_success`: 단일 CLI operation이 artifact kind, canonical target identity, complete candidate content를 명시적으로 받아 `micro-spec`, `iteration-qc`, `delivery-qc` 중 정확히 하나의 requested family를 식별한다.
- `required_preconditions`: configured canonical roots와 allowed artifact kinds가 존재하고 invocation은 one kind, one canonical target, one complete content input을 제공한다.
- `mutation_boundary`: parsing과 request validation은 read-only이며 success 시에도 requested family의 new canonical target 하나 외에는 변경하지 않는다.
- `negative_behavior`: unknown kind, malformed or ambiguous identity, absolute path, traversal, alias 또는 incomplete content는 structured blocker로 reject되고 target은 absent로 남는다.
- `direct_evidence`: isolated copied-fixture CLI tests가 accepted request와 each invalid request의 structured result 및 target absence를 assert한다.
- `dependencies`: none
- `completion_group`: CG-1: all issuance controls are jointly verified before any implementation-ready claim
- `candidate_micro_spec`: ms-0003-002
- `non_goals`: implicit identifier allocation, target scanning/increment, batch issuance 또는 lifecycle authority issuance를 제공하지 않는다.

### AC-002 — pre-publication validation and authority boundary

- `observable_success`: filesystem mutation 전에 candidate schema/semantic contract, canonical target binding, parent path/ID/revision/digest 및 family prerequisite가 모두 validate되고 CLI/help/guidance가 issuance의 non-authorizing boundary를 명시한다.
- `required_preconditions`: AC-001 explicit request contract, canonical validator primitives, complete candidate content와 applicable parent evidence가 존재한다.
- `mutation_boundary`: validation failure는 canonical target directory entry를 만들지 않으며 approved/historical artifacts, approval/confirmation/adoption records를 변경하지 않는다.
- `negative_behavior`: invalid candidate, missing/stale/mismatched parent, unsafe path 또는 unmet prerequisite는 machine-readable code/path/detail을 반환하고 requested target을 absent로 남긴다.
- `direct_evidence`: copied-fixture tests가 each pre-publication blocker와 no-target-mutation assertion을 실행하고 CLI help/template text를 contract assertions으로 검증한다.
- `dependencies`: AC-001
- `completion_group`: CG-1: all issuance controls are jointly verified before any implementation-ready claim
- `candidate_micro_spec`: ms-0003-002
- `non_goals`: approval, confirmation, adoption, merge, delivery 또는 release claim을 만들거나 live control plane을 adopt하지 않는다.

### AC-003 — pre-adoption Micro-SPEC issuance policy

- `observable_success`: canonical `micro-spec` issuance는 exact current approved REQ path, ID, revision, final SHA-256, status와 valid approval binding을 확인한 뒤 non-claiming planning artifact만 publish한다.
- `required_preconditions`: AC-001/AC-002가 complete이고 parent REQ는 canonical approved snapshot이며 production adoption registry는 pre-adoption state를 유지한다.
- `mutation_boundary`: success는 requested Micro-SPEC target 하나만 만들며 parent REQ, approval, adoption registry와 existing evidence bytes를 변경하지 않는다.
- `negative_behavior`: unapproved, missing, malformed, digest-mismatched, superseded/invalid 또는 noncanonical parent는 target mutation 없이 distinct structured blocker로 reject된다.
- `direct_evidence`: copied-fixture positive Micro-SPEC issuance와 each invalid-parent rejection test가 path, digest, no-mutation 및 non-claiming content를 assert한다.
- `dependencies`: AC-001, AC-002

### AC-004 — iteration-QC and delivery-QC prerequisite policy

- `observable_success`: `iteration-qc`와 `delivery-qc` issuance는 copied fixture의 applicable adopted control-plane registry와 complete canonical parent graph를 resolve한 뒤에만 requested QC artifact를 publish한다.
- `required_preconditions`: AC-001/AC-002, exact approved REQ and approval binding, applicable adoption evidence, and for iteration-QC an exact Micro-SPEC parent; delivery-QC requires all referenced iteration-QC/Micro-SPEC edges.
- `mutation_boundary`: parent graph/adoption validation is read-only; successful publication may create only the requested QC target in a copied fixture.
- `negative_behavior`: missing, mismatched, stale, malformed, unsafe, semantically invalid, unapproved, unadopted or approval-record-invalid parent data is rejected before target mutation with a distinct structured blocker.
- `direct_evidence`: copied-fixture tests prove pre-adoption rejection, adopted valid iteration-QC/delivery-QC issuance, and graph-edge failure target absence.

- `candidate_micro_spec`: ms-0003-002
- `non_goals`: production adoption mutation, live QC issuance, or inference of implementation/delivery completion from a created QC artifact.

### AC-005 — canonical safe path and immutable publication

- `observable_success`: issuance derives only the configured canonical target path and uses atomic exclusive creation so one same-host/local-filesystem competing writer wins while the loser returns a duplicate/conflict blocker without changing the winner.
- `required_preconditions`: AC-001 explicit target, validated family-specific prerequisites, configured canonical root on the supported same-host/local-filesystem boundary.
- `mutation_boundary`: success writes only a previously absent requested leaf; symlinked leaf/intermediate path, parent-directory swap, escape path, pre-existing target and loser process output remain untouched.
- `negative_behavior`: unsafe paths, pre-existing targets and competing publication attempts fail without overwrite; the operation does not rely on `Path.exists()` followed by a write.
- `direct_evidence`: copied-fixture tests cover absolute/traversal/symlink/intermediate-symlink rejection and deterministic competing-process one-winner/no-mutating-loser behavior.
- `dependencies`: AC-001, AC-002, AC-003, AC-004
- `completion_group`: CG-1: all issuance controls are jointly verified before any implementation-ready claim
- `candidate_micro_spec`: ms-0003-002
- `non_goals`: distributed, multi-host, network-filesystem, external-lock or cross-repository concurrency guarantees.

### AC-006 — no partial target after failed operation

- `observable_success`: success fsyncs completed file and containing directory, recomputes the final published SHA-256, and every specified controlled failure leaves no visible target owned by the failed operation.
- `required_preconditions`: AC-005 atomic exclusive publication primitive and ownership identity available before cleanup; failures are exercised only in isolated temporary/copied fixtures.
- `mutation_boundary`: cleanup may remove only the target inode published by the failing operation and must never remove a competing writer's target.
- `negative_behavior`: candidate/schema/semantic validation failure, unsafe path, competition, interrupted write, flush/fsync failure or post-write validation failure leaves no partial owned canonical target and reports failure rather than success.
- `direct_evidence`: fault-injection tests cover write/flush/fsync/post-write-validation failure, assert target absence, and assert competing winner bytes survive.
- `dependencies`: AC-005
- `completion_group`: CG-1: all issuance controls are jointly verified before any implementation-ready claim
- `candidate_micro_spec`: ms-0003-002
- `non_goals`: recovery by overwrite, delete-and-retry, repair of an existing target, or guarantees outside controlled same-host/local-filesystem failures.

### AC-007 — exact structured result and no overwrite retry

- `observable_success`: successful result returns artifact kind, canonical safe-relative path, canonical identity and recomputed SHA-256 of exact published bytes; repeating a successful request returns duplicate/conflict rather than idempotent success.
- `required_preconditions`: AC-005 and AC-006 successful publication and final digest computation complete for the requested artifact.
- `mutation_boundary`: repeat and duplicate paths are read-only failures; a success records no authority-bearing lifecycle status beyond the issued planning/QC evidence itself.
- `negative_behavior`: duplicate requests do not compare content for idempotent success, overwrite, replace, delete, reuse or mutate the existing target.
- `direct_evidence`: copied-fixture tests recompute reported digest from published bytes and assert repeated request failure plus unchanged target bytes.
- `dependencies`: AC-005, AC-006
- `completion_group`: CG-1: all issuance controls are jointly verified before any implementation-ready claim
- `candidate_micro_spec`: ms-0003-002
- `non_goals`: status transition, approval evidence, adoption entry, implementation result, merge, delivery or release record issuance.
