# REQ: canonical evidence issuance 및 immutable-write safety

> **Lifecycle boundary:** 이 requirement는 정확히 confirmed된 Discovery `dcy-0003-r1`에서 파생되었다. draft issuance는 review, rejection, approval, implementation, adoption, merge, delivery 또는 release authority가 아니다. 이후 lifecycle decision은 각각 정확한 관련 artifact bytes에 binding된 별도의 governed content-addressed record여야 한다. 이 requirement의 material change에는 새 REQ revision이 필요하며, 이 draft는 이전 approved artifact를 amend하지 않는다.

## 1. 목표 (Goal)

isolated greenfield 또는 copied-fixture repository에서만, 완전히 validation된 canonical evidence artifact 하나를 atomic하게 publish하는 repository-local artifact-kind-selected SpecBound issuance interface를 구현한다. copied fixture는 adoption-gated QC issuance를 검증하기 위해 이미 adopted된 control plane을 synthetic하게 모델링할 수 있으나, 이 REQ는 live repository를 adoption하지 않으며 live adopted repository에서의 issuance를 authorize하지 않는다. interface는 mutation 전 모든 authorization, parent graph, semantic 및 filesystem precondition을 validation하고, 성공 시 canonical safe-relative path와 정확한 SHA-256만 report하며, rejection 또는 controlled write failure 후 canonical target을 남기지 않아야 한다.

## 3. 범위 (Scope)

### In scope

- 하나의 명시적인 artifact-kind-selected CLI issuance operation. invocation마다 명시적 canonical target identity 하나와 complete artifact-content input 하나를 받아야 하며, implicit identifier를 allocate하거나 현재 filesystem에서 target을 infer해서는 안 된다.
- 다음 세 artifact family에 대한 canonical issuance:
  - `.specbound/micro-specs/` 아래의 planning-only `micro-spec`;
  - `.specbound/iteration-qc/` 아래의 `iteration-qc`;
  - `.specbound/delivery-qc/` 아래의 `delivery-qc`.
- filesystem publication 전에 candidate artifact와 적용 가능한 모든 canonical parent의 완전한 schema 및 semantic validation.
- safe-relative path enforcement, symlink containment protection, atomic exclusive publication, ownership-safe failure cleanup, structured blocker result 및 success digest reporting.
- executable issuance contract를 위한 repository-local template, CLI/help documentation, authoring guidance, isolated copied-fixture test 및 regression coverage.

### Non-goals

- approval 또는 confirmation issuance, REQ 상태를 `approved`로 변경, approval/confirmation/rejection/adoption/merge/delivery-decision/release record 생성 또는 수정.
- manual-bootstrap 또는 기존 adopter artifact의 수정, migration, relabelling, import 또는 enrollment.
- automatic target numbering, batch issuance, existing target repair, overwrite, replace, delete 또는 retry-by-mutation semantics.
- distributed, multi-host, network-filesystem, external-lock 또는 cross-repository concurrency guarantee.
- live control-plane adoption, live Hermes-profile rollout, tracker integration, external signing, merge 또는 release.

## 4. Acceptance criteria

- **AC-001 — 명시적 canonical request contract:** CLI는 invocation마다 requested artifact family 하나, explicit canonical target identity 하나, complete candidate-content input 하나를 갖는 artifact-kind-selected issuance operation 하나를 제공해야 한다. `micro-spec`, `iteration-qc`, `delivery-qc`에 대해 configured canonical form만 받아야 하며 unknown kind, malformed ID, ambiguous/multiple target, absolute path, traversal, noncanonical alias 및 완전한 validation에 실패한 content를 reject해야 한다. 기존 artifact scan 또는 increment로 target을 선택해서는 안 된다.

- **AC-002 — publication 전 validation 및 authority boundary:** target directory entry를 만들기 전에 issuance는 candidate artifact의 schema 및 semantic contract, canonical target/path/identity binding, 필요한 모든 parent path/ID/revision/digest, 그리고 family-specific prerequisite를 validation해야 한다. command는 approval, confirmation, adoption, merge, delivery 또는 release claim을 만들지 않아야 하며 CLI/help와 artifact guidance에 이 narrow authority boundary를 report해야 한다. 모든 pre-publication blocker는 structured machine-readable code/path/detail evidence를 반환하고 requested target을 absent 상태로 남겨야 한다.

- **AC-003 — Micro-SPEC issuance policy:** `micro-spec` issuance는 canonical path, ID, revision, final SHA-256, status 및 valid approval binding을 포함하는 정확한 current approved parent REQ를 요구해야 한다. control-plane adoption 이전에는 selected Acceptance criteria와 정확한 approved REQ에 binding되고 명시적으로 non-claiming인 complete planning artifact만 발급할 수 있다. unapproved, missing, malformed, digest-mismatched, superseded/invalid 또는 비canonical REQ parent는 target mutation 없이 reject해야 한다. resulting Micro-SPEC는 iteration verification, delivery verification, adoption, merge 또는 release authority를 assert해서는 안 된다.

- **AC-004 — iteration-QC 및 delivery-QC prerequisite policy:** `iteration-qc`와 `delivery-qc` issuance는 copied fixture의 applicable adopted control-plane registry에 정확한 parent REQ가 없으면 reject해야 한다. mutation 전에 두 QC path 모두 complete canonical parent graph를 그 REQ까지 resolve하고 REQ의 canonical path, ID, revision, final SHA-256, `approved` status 및 정확한 valid approval record binding을 validation해야 한다. `iteration-qc`는 추가로 정확한 canonical Micro-SPEC parent와 Micro-SPEC의 approved-REQ binding을 validation해야 하며, `delivery-qc`는 정확한 canonical REQ parent와 참조하는 모든 iteration-QC/Micro-SPEC graph edge를 validation해야 한다. missing, mismatched, stale, superseded, malformed, unsafe, semantically invalid 또는 approval-record-absent/invalid parent data는 distinct structured blocker category와 no target mutation을 만들어야 한다. 두 kind 모두 publication 전에 required parent path, ID, revision, SHA-256, schema validity, semantic validity, selected/covered Acceptance criteria 및 applicable adoption condition을 validation해야 한다.

- **AC-005 — canonical safe path 및 immutable publication:** issuance는 requested family에 대해 configured canonical path만 derive하고 symlinked leaf 또는 intermediate component, parent-directory swap, path escape 및 pre-existing target을 reject해야 한다. 지원하는 same-host, same-local-filesystem boundary에서 publication은 atomic exclusive creation을 사용해야 한다. 같은 canonical target을 대상으로 하는 competing writer에서는 정확히 하나만 artifact를 성공시키고, 패배한 writer는 winner를 수정하지 않는 structured duplicate/conflict blocker를 반환해야 한다. no-overwrite 또는 containment control로 `Path.exists()`-then-write sequence에 의존해서는 안 된다.

- **AC-006 — failure 시 partial target 부재:** candidate validation failure, content/schema/semantic failure, unsafe-path rejection, competing-target failure, interrupted write, flush/fsync failure 또는 post-write validation failure는 failed operation이 소유한 visible canonical target을 남기지 않아야 한다. cleanup은 ownership-safe해야 하며 competing writer가 publish한 target을 삭제해서는 안 된다. implementation은 success를 report하기 전에 completed file과 containing directory를 fsync하고, exact published bytes의 final SHA-256을 recompute하여 report해야 한다.

- **AC-007 — 정확한 output 및 non-idempotent overwrite 금지:** successful result는 artifact kind, canonical safe-relative path, canonical identity 및 published artifact의 SHA-256을 포함한 structured data를 반환해야 한다. success 뒤 같은 request를 반복하면 idempotent success가 아니라 duplicate/conflict failure여야 하며 content comparison 또는 overwrite operation이 되어서는 안 된다. command는 successful draft/planning 또는 QC artifact issuance를 넘어서는 authority-bearing status를 emit해서는 안 된다.

- **AC-008 — template, guidance 및 behavioral evidence:** repository-local template과 authoring/CLI guidance는 implemented command 및 family-specific parent/adoption rule과 일치해야 한다. isolated copied-fixture test는 최소한 다음을 증명해야 한다: approved REQ에서 valid planning-only pre-adoption Micro-SPEC issuance; pre-adoption iteration-QC와 delivery-QC rejection; complete valid parent graph를 가진 adopted iteration-QC와 delivery-QC issuance; malformed/missing/digest-mismatched/semantically invalid parent rejection; invalid candidate-content rejection; absolute/traversal/symlink/intermediate-symlink rejection; duplicate target refusal; one winner 및 non-mutating loser를 갖는 deterministic competing-process race; target 없는 forced write/flush/fsync failure; exact reported-digest verification; 그리고 unchanged live adoption registry. artifact를 만드는 test는 repository canonical root가 아닌 copied 또는 temporary fixture를 사용해야 한다.

## 5. Design constraint 및 결정

1. **Single generic surface:** 초기 interface는 중복된 세 filesystem writer가 아니라 하나의 artifact-kind-selected issuance operation이다. family-specific schema, semantic, parent, adoption check는 명시적이며 독립적으로 testable하게 유지한다.
2. **Input-before-write:** operation은 complete candidate content를 consume한다. placeholder를 publish한 뒤 후속 manual edit로 artifact를 valid하게 만드는 방식은 허용하지 않는다.
3. **Greenfield 및 copied-fixture first:** 최초 implementation은 production `control_plane_adoption.requirements: []` registry를 보존하고 existing canonical/manual-bootstrap evidence를 mutation하지 않아야 한다.
4. **Pre-adoption distinction:** approved REQ는 adoption 이전에 non-claiming canonical Micro-SPEC만 받을 수 있다. adoption이 valid해질 때까지 iteration-QC 또는 delivery-QC issuance는 허용되지 않는다.
5. **No implied lifecycle decision:** valid artifact write는 evidence issuance일 뿐이다. implementation success, approval, adoption, merge, delivery, release 또는 후속 action authority를 establish할 수 없다.
6. **Concurrency boundary:** exclusive-create guarantee는 한 host와 한 local filesystem에서 경쟁하는 process에만 적용된다. 다른 concurrency model은 explicit non-goal이며 implied support가 아니다.
7. **No mutation recovery:** duplicate 또는 failed request는 target replace/delete/reuse로 repair하지 않는다. 이후 legitimate change는 separately governed scope 아래 fresh target/revision을 요구한다.

## 6. 검증 계획 (Verification plan)

- focused issuance test와 full repository suite에는 `.venv/bin/python -m pytest`를 사용한다.
- repository root와 isolated valid/negative copied fixture에는 `.venv/bin/python -m specbound.cli preflight` 및 `.venv/bin/python -m specbound.cli validate`를 사용한다.
- temporary/copied fixture repository에서 real source 또는 installed CLI probe를 실행하여 success, 선언한 모든 fail-closed blocker, same-target race behavior, controlled write-failure cleanup을 검증한다.
- 각 successful published file에서 SHA-256을 recompute하고 CLI structured output과 비교한다.
- production `specbound.yaml` adoption registry가 empty 상태로 유지되고 existing approved 또는 manual-bootstrap artifact bytes가 바뀌지 않았음을 검증한다.
- `git diff --check`를 실행하고 topology, documentation, template, implementation-contract consistency를 위해 final diff를 검토한다.
