## 3. Scope

### In scope

- Canonical topology: Markdown Micro-SPECs at `.specbound/micro-specs/req-<id>/ms-<id>-<slice>.md`; JSON iteration-QC records at `.specbound/iteration-qc/req-<id>/iqc-<id>-<slice>-r<revision>.json`; and JSON delivery-QC records at `.specbound/delivery-qc/req-<id>/dqc-<id>-r<revision>.json`. In every filename, `<id>` is the exact numeric component of the bound `req-<id>`, `<slice>` is a positive decimal slice number, and `<revision>` is a positive decimal record revision.
- Versioned schemas: each Micro-SPEC Markdown document has YAML frontmatter with `schema_version: 1`; each iteration-QC and delivery-QC JSON object has `schema_version: 1`.
- Content-addressed bindings appropriate to each transition: an approved REQ snapshot for a Micro-SPEC; a Micro-SPEC snapshot plus selected acceptance criteria for iteration QC; and the approved REQ snapshot plus verified iteration-QC evidence for delivery QC.
- Safe deterministic validation of identity, revision, paths, schema, digest, status, selected acceptance criteria, and required evidence; malformed, stale, mismatched, unsafe, or symlinked artifacts fail closed.
- An explicit opt-in adoption/version boundary so absence of the new artifacts for pre-adoption REQs is not classified as malformed, while adopted REQs cannot claim iteration or delivery progress without the required evidence.
- Isolated fixture coverage, templates, configuration, documentation, and repository-local skill guidance aligned with the executable contract.
- Lifecycle-state correction only: supersede r1 for review purposes without modifying r1's exact approved bytes or expanding authority.

### Out of scope

- Approval, rejection, or revision of a Discovery or REQ; this REQ consumes the existing approved-REQ binding model.
- Automatic migration or retrospective canonicalization of manual-bootstrap Micro-SPEC/QC evidence, including `req-0002`; any later adoption must be explicit and must preserve its original evidence boundary.
- Delivery decision, merge authorization, merge execution, release execution, release provenance, tracker integration, external signing, and live Hermes-profile rollout.
- Treating a delivery-QC pass as authority to merge or release.
- Canonical artifact issuance/write automation, including artifact target allocation and no-overwrite create semantics; that is separately scoped by draft Discovery `dcy-0003-r1`.

## 4. Acceptance criteria

- **AC-001 — Canonical topology and schema contract:** The repository must define and validate exactly these three families: Markdown Micro-SPECs at `.specbound/micro-specs/req-<id>/ms-<id>-<slice>.md` with YAML-frontmatter `schema_version: 1`; JSON iteration-QC records at `.specbound/iteration-qc/req-<id>/iqc-<id>-<slice>-r<revision>.json` with object field `schema_version: 1`; and JSON delivery-QC records at `.specbound/delivery-qc/req-<id>/dqc-<id>-r<revision>.json` with object field `schema_version: 1`. `<id>` must exactly match the bound REQ numeric identifier; `<slice>` and `<revision>` must be positive decimal numbers. Each schema must reject absolute/traversal/noncanonical paths and symlinked components, and must distinguish human-readable planning source from machine-readable QC/control data. Templates, configuration, documentation, and validator constants must agree exactly.

- **AC-002 — Micro-SPEC binding and planning completeness:** A canonical Micro-SPEC must bind exactly one approved REQ path, ID, revision, and SHA-256 snapshot; name only selected, currently in-scope acceptance-criterion IDs; and record objective, scope, explicit non-goals, baseline, verification plan, QC exit rule, and rollback/containment where risk warrants it. Validation must reject an unapproved/mismatched parent, altered parent digest, duplicate/noncanonical target, unknown or duplicate selected AC, or incomplete required planning content.

- **AC-003 — Iteration-QC evidence contract:** A canonical iteration-QC record must bind the exact Micro-SPEC snapshot it evaluates, preserve its selected AC set, identify the focused verification commands/results and QC verdict, and enumerate remaining or unfulfilled ACs. Only a `verified` verdict with complete reproducible evidence may contribute coverage to delivery QC. The validator must reject evidence with a stale/mismatched Micro-SPEC digest, AC-set mismatch, malformed verdict/result, missing focused evidence, or a record that attempts to cover ACs outside its Micro-SPEC.

- **AC-004 — Delivery-QC aggregation contract:** A canonical delivery-QC record must bind one approved REQ snapshot, map every required REQ acceptance criterion to one or more verified iteration-QC records, retain cross-iteration regression evidence, identify reviewer or risk-policy-permitted delegated authority, and list unresolved exceptions/residual-risk disposition. The validator must fail closed if any required AC lacks verified coverage, any referenced iteration evidence is invalid or bound to another REQ snapshot, regression evidence is absent, authority is not permitted by policy, or the record implies merge/release authority.

- **AC-005 — Adoption boundary and compatibility:** The configuration and validator must define an explicit versioned adoption condition for the new control plane. Non-adopted historical REQs remain valid without Micro-SPEC/QC artifacts; after adoption, missing or malformed required artifacts block only the relevant iteration/delivery claim. Existing manual-bootstrap records remain non-canonical unless a later, explicitly governed migration/adoption process defines their treatment. No validator change may silently rewrite, invalidate, or relabel historical REQ/approval/Discovery evidence.

- **AC-006 — Executable fail-closed evidence:** Isolated valid and negative fixtures plus the real repository CLI must demonstrate a complete adopted evidence-validation happy path and failures for unsafe paths/symlinks, malformed schemas, duplicate targets, parent/digest/ID/revision mismatch, unknown or incomplete AC coverage, invalid iteration verdict/evidence, invalid delivery aggregation, unauthorized authority, and pre-adoption absence. The focused suite, full repository suite, `specbound.cli preflight`, `specbound.cli validate`, and whitespace/diff checks must pass. Documentation and skills must not claim that manual QC, iteration QC, or delivery QC authorizes merge or release. Canonical artifact issuance/write behavior is not asserted by this criterion and is separately governed by `dcy-0003-r1`.

## 5. Design constraints and decisions

1. **Separate canonical owners and fixed representation:** Micro-SPEC planning uses Markdown plus YAML frontmatter at `.specbound/micro-specs/req-<id>/ms-<id>-<slice>.md`; iteration QC uses JSON at `.specbound/iteration-qc/req-<id>/iqc-<id>-<slice>-r<revision>.json`; and delivery QC uses JSON at `.specbound/delivery-qc/req-<id>/dqc-<id>-r<revision>.json`. A REQ remains the canonical owner of scope and acceptance criteria, and a delivery decision/merge/release remains outside this REQ.
2. **Minimum necessary snapshot binding:** Transition-authorizing or immutable-snapshot-attesting records use SHA-256 binding to the exact required parent snapshot. Ordinary references use stable identifiers/revisions only where a digest would not be needed for the transition's integrity.
3. **No inferred coverage:** Delivery coverage is derived only from validated `verified` iteration-QC records whose selected ACs match their bound Micro-SPEC and whose REQ lineage matches the delivery-QC parent.
4. **Fail closed at the adoption boundary:** Before explicit adoption, missing new artifacts are not errors. After adoption, malformed/missing/cross-boundary artifacts block the affected lifecycle claim rather than being ignored.
5. **Narrow authority:** Neither a Micro-SPEC nor either QC artifact authorizes approval, delivery decision, merge, or release. Human/delivery-system authority remains a separate future boundary.
6. **Bootstrap evidence remains labelled:** Existing manual-bootstrap evidence may be cited as historical context but must not be converted, relabelled, or treated as canonical without a separately approved migration/adoption decision.
7. **Revision exception is historical only:** The r1 supersession exception preserves only its exact approved bytes as historical implementation-verification evidence. It does not approve this r2 draft, authorize new implementation, or alter the non-adopted production registry.
